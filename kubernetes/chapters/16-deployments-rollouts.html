Deployments and rollouts

A Deployment never touches a pod directly — it manages ReplicaSets, and keeps the old ones around, scaled to zero, as the entire mechanism a rollback actually uses. This chapter is that machinery, the two budgets that pace a rollout, and what happens when one gets stuck.

16.1 A Deployment doesn't manage pods — it manages ReplicaSets

It's tempting to think of a Deployment as "the thing that manages your pods," and skip a layer that turns out to matter. A Deployment's actual, direct children are ReplicaSets (Chapter 5's scheduler places pods; the ReplicaSet from Chapter 1's example is what maintains their count). A Deployment doesn't touch pods at all — it creates and scales ReplicaSets, and each ReplicaSet is the one actually creating and deleting pods to match its own replica count.

Deployment "web"
  └── ReplicaSet "web-7f9c4d8b6"  (revision 3, current)  replicas: 5
  └── ReplicaSet "web-5b8d9c7f4"  (revision 2, old)        replicas: 0
  └── ReplicaSet "web-6c7a8e9d1"  (revision 1, old)         replicas: 0

Every revision the Deployment has ever rolled out to keeps its own ReplicaSet object around, scaled to zero once superseded, rather than being deleted — and that retained history, not some separate log, is literally what a rollback rolls back to: scale the old ReplicaSet back up, scale the current one down. revisionHistoryLimit (default 10) caps how many of these old, zeroed ReplicaSets stick around before the oldest get garbage collected — set it to 0 and rollback stops being possible at all, because there's nothing left to roll back to.

16.2 Rolling update: two knobs controlling one trade-off

The default strategy, RollingUpdate, replaces old pods with new ones gradually rather than all at once, governed by exactly two numbers that trade off capacity against risk:

FieldControlsDefault
maxSurgeHow many pods above the desired count are allowed to exist during the rollout25%
maxUnavailableHow many pods below the desired count are tolerated during the rollout25%

maxSurge: 0 forces old pods to be removed before any new one starts — never exceeding the original count, at the cost of dipping below it while the rollout proceeds. maxUnavailable: 0 forces the opposite: never fewer than the desired count are ready, at the cost of briefly exceeding it. maxSurge: 0 paired with maxUnavailable: 1 (rather than 0) is the genuinely slow, capacity-constrained configuration — never above the desired count, replacing exactly one pod at a time. Setting both to 0 is not a valid configuration at all: the API server rejects it outright, because neither budget would ever be able to create room to swap even a single pod — nothing could be removed without first being replaced, and nothing could be created without first making room.

16.4 Two conditions decide whether a rollout is actually stuck

A Deployment reports its state through status.conditions, and the one that actually answers "is this rollout healthy" is Progressing. A rollout that stalls — new pods perpetually failing readiness, an image that can't be pulled — doesn't hang forever silently; after progressDeadlineSeconds (default 600) with no forward progress, Progressing flips to False with reason ProgressDeadlineExceeded. Critically, this does not stop or roll back the rollout automatically — the broken new ReplicaSet keeps trying, old pods stay around holding the line on maxUnavailable, and the cluster sits in a stable-but-degraded holding pattern until a human intervenes with a rollback or a fix.

kubectl rollout status deployment/web
# Waiting for deployment "web" rollout to finish: 2 out of 4 new replicas
# have been updated...
# (after progressDeadlineSeconds with no change)
# error: deployment "web" exceeded its progress deadline

16.5 Lab · read a rollout's real state and roll it back

Shell · revisions, rollback, and a stuck rollout
# The ReplicaSets a Deployment actually owns, old ones scaled to zero
kubectl get rs -l app=web
#   web-7f9c4d8b6   5   5   5   2m    <- current
#   web-5b8d9c7f4   0   0   0   1h    <- previous revision, kept for rollback
#   web-6c7a8e9d1   0   0   0   3h

# Revision history and what changed at each one
kubectl rollout history deployment/web
kubectl rollout history deployment/web --revision=2

# Roll back to the previous revision - this scales an old ReplicaSet
# back up and the current one down, nothing more exotic than that
kubectl rollout undo deployment/web
kubectl rollout undo deployment/web --to-revision=2

# Watch Progressing flip when a rollout stalls
kubectl get deployment web -o jsonpath='{.status.conditions[?(@.type=="Progressing")]}'
#   reason: ProgressDeadlineExceeded  <- stuck, not auto-rolled-back

# Pause a rollout mid-flight to inspect it without racing further changes
kubectl rollout pause deployment/web
kubectl rollout resume deployment/web

# Confirm the actual surge/unavailable budget in effect
kubectl get deployment web -o jsonpath='{.spec.strategy.rollingUpdate}'

Knowledge check

A Deployment's rollout is rolled back to the previous version. What actually happens underneath?

Every revision's ReplicaSet sticks around, scaled to zero, up to revisionHistoryLimit. A rollback is just the same scale-up/scale-down mechanism a normal rollout uses, pointed at an old ReplicaSet instead of a new one — there's no separate rollback-specific machinery.

A Deployment is configured with revisionHistoryLimit: 0. What is the direct consequence?

Rollback depends entirely on a previous revision's ReplicaSet object still existing. Setting the retention limit to zero means nothing is kept once superseded, so there is nothing left for kubectl rollout undo to scale back up.

A Deployment's rollout stalls because new pods keep failing readiness. After progressDeadlineSeconds elapses, what happens automatically?

progressDeadlineSeconds only changes what's reported, not what's done — it's a detection mechanism, not a remediation one. The broken rollout keeps running exactly as it was; a human (or separate automation) has to decide whether to fix the underlying issue or explicitly roll back.

A Deployment with 4 desired replicas is submitted with maxSurge: 0 and maxUnavailable: 0. What happens?

This combination looks plausible — "never exceed, never dip below" — but it's a genuine deadlock: removing an old pod first would drop below the desired count (forbidden by maxUnavailable: 0), and creating a new pod first would exceed it (forbidden by maxSurge: 0). Kubernetes' validation catches this at admission time rather than letting a rollout hang forever with no legal first move.

16.6 What to carry into Chapter 17

  • A Deployment manages ReplicaSets, not pods directly — each ReplicaSet still does the pod-count reconciliation from Chapter 1.
  • Old ReplicaSets are retained, scaled to zero, up to revisionHistoryLimit — that retained history is the entire rollback mechanism, not a separate log.
  • maxSurge and maxUnavailable trade capacity against risk during a rollout; zero on both still works, just strictly serially.
  • A stalled rollout is detected (Progressing/ProgressDeadlineExceeded) but never auto-remediated — it holds in a degraded state until something acts on it.

Every rollout so far has assumed the new pods only differ in image or resource fields. The next chapter is what happens when what actually needs to change is configuration — and the surprising ways a config update does, and does not, reach an already-running pod.
