Container runtimes

Somewhere below every 'start this container' call sits an interface, two specifications, and a filesystem trick that lets a thousand containers share almost everything they need without copying it once. This chapter is that stack, from the kubelet's request down to a process the kernel actually runs.

8.1 The interface that ended the runtime wars

Early Kubernetes talked to Docker directly, through code baked into the kubelet itself. Every alternative runtime someone wanted to use — and there were real reasons to want alternatives, from security isolation to raw performance — meant patching the kubelet's own source. The Container Runtime Interface (CRI) replaced that with a gRPC API the kubelet speaks to any compliant runtime: a small, stable set of calls — RunPodSandbox, CreateContainer, StartContainer, StopContainer, image pull and status calls — that the kubelet issues without knowing or caring which runtime is on the other end.

This is the same architectural move Chapter 2 described for the API server: push every runtime-specific detail behind one stable interface, so the two sides can evolve independently. It is also why "which container runtime does this cluster use" stopped being a question with implications for the rest of Kubernetes — containerd, CRI-O, and others are all just CRI implementations, interchangeable from the kubelet's point of view.

kubelet  --(CRI, gRPC)-->  containerd  --(OCI runtime spec)-->  runc  --(syscalls)-->  kernel
                                │
                                └── containerd-shim, one per container,
                                    keeps it alive if containerd itself restarts

8.2 Two specs, two different jobs

"OCI" names two separate specifications that are easy to conflate because both ship under the same umbrella and both matter to every container that runs.

SpecAnswersConsumed by
OCI Image SpecWhat does a container image look like on disk — layers, a manifest, a config blob describing the entrypoint and environmentRegistries, and whatever pulls and unpacks an image (containerd's own pull path)
OCI Runtime SpecGiven an already-unpacked root filesystem and a JSON config, how do you actually start it as an isolated process — namespaces, cgroups, mounts, capabilitiesThe low-level runtime — runc, or an alternative like crun or gVisor

containerd's job is the bridge between them: pull an OCI image, unpack its layers into a root filesystem, translate the result into an OCI runtime spec's config.json, then hand that to runc, which does the actual namespace and cgroup setup and executes the process. Nothing about the image format has anything to say about how isolation is implemented, and nothing about the runtime spec knows what a registry or an image layer is — that separation is deliberate, and it is what lets something like gVisor or Kata Containers swap in as a drastically different runtime — a sandboxed VM, in Kata's case — while still consuming the exact same OCI Runtime Spec config that runc does.

8.3 Layers, and why a pull is rarely a full download

An image is not one blob — it is an ordered stack of layers, each one a filesystem diff, referenced by content-addressable digest. Two images sharing a base layer (the same python:3.12-slim, say) share that layer's actual bytes on disk and on the wire; a node that already has it cached pulls nothing for that layer at all, regardless of which image asked for it.

Interactive · image pull, layer by layeridle
myapp:v3 = base:alpine + runtime:python3.12 + deps:sha91a + app:sha77f. Click "Pull" to see which layers actually transfer.
This is why a CI pipeline that rebuilds only application code, on top of a stable, widely-used base image, produces near-instant deploys across a fleet: every node has almost every layer already, and the pull is really just the last one or two.

8.4 Snapshotters: unpacking layers without copying them twice

Downloading layers is only half the work — they also need to be assembled into the single root filesystem a container actually runs against, without duplicating every shared layer's bytes on disk for every container that uses it. This is a snapshotter's job, and overlayfs is the default on Linux: each layer is a read-only directory, and containerd stacks them with an overlay union mount that presents them as one filesystem, adding one thin writable layer on top for whatever the running container actually changes.

Nothing is copied to build this stack — the underlying layer directories are shared, read-only, across every container using them, and only writes go anywhere new. This is also precisely why a container's filesystem changes vanish when the container is removed unless a volume was explicitly mounted over the relevant path: the writable layer is deleted along with the container, and the read-only layers underneath were never touched in the first place.

8.5 Lab · watch CRI calls and layers from outside containerd

Shell · crictl, the CRI-native equivalent of docker CLI commands
# crictl talks CRI directly — this is genuinely what the kubelet is calling
crictl ps                       # running containers, per the runtime, not the API server
crictl pods                     # pod sandboxes — the shared network namespace CRI creates per pod
crictl images                   # what's actually cached on this node right now

# Pull, and watch layer-level reuse for yourself
crictl pull docker.io/library/python:3.12-slim
crictl imagefs-info | jq .      # disk usage of the image store, snapshotter included

# Inspect the actual OCI runtime spec containerd handed to runc for a
# running container — this is the literal config.json from 8.2
crictl inspect  | jq '.info.runtimeSpec.linux.namespaces'
crictl inspect  | jq '.info.runtimeSpec.linux.resources'

# Confirm which runtime a cluster is actually using — the same CRI
# regardless of the answer
kubectl get node node-1 -o jsonpath='{.status.nodeInfo.containerRuntimeVersion}'

# See the layer stack of a local image directly
crictl inspecti python:3.12-slim | jq '.status.size, .info.imageSpec'

Knowledge check

What problem did the Container Runtime Interface (CRI) actually solve?

Before CRI, runtime-specific logic lived inside the kubelet itself, so any alternative runtime meant changing kubelet code. CRI is a stable gRPC interface that any compliant runtime implements, letting the kubelet stay runtime-agnostic — architecturally the same move the API server makes for cluster state in Chapter 2.

Which pairing correctly matches an OCI specification to the layer of the system that actually consumes it?

The Image Spec is about what a container looks like at rest — layers, manifest, config blob. The Runtime Spec is about turning an already-unpacked filesystem into a running, isolated process — namespaces, cgroups, mounts. containerd bridges the two; runc (or a swap-in like gVisor or Kata) only ever sees the runtime spec side.

Two images on the same node share an identical base layer. A node that already has that base layer cached pulls a new image built on it. What happens to that shared layer?

Layers are content-addressable and shared across any image that references the same digest. A pull only fetches layers the node doesn't already have; a cached base layer is reused untouched, which is why images sharing a common, already-deployed base pull dramatically faster than their total uncompressed size would suggest.

A running container writes a large temporary file to its own filesystem (no volume mounted at that path), then the container is deleted. What happens to that file?

The overlay snapshotter gives every container exactly one writable layer, stacked on top of shared, read-only image layers. Anything the container writes lands only in that thin top layer, which is discarded when the container is removed — the underlying shared layers, used by every other container built from the same image, are never modified.

8.6 What to carry into Chapter 9

  • CRI is a stable gRPC interface between the kubelet and any compliant runtime — the same "push variation behind an interface" pattern the API server applies to cluster state.
  • The OCI Image Spec (what an image looks like) and OCI Runtime Spec (how to run one as an isolated process) are two different specifications with two different consumers, bridged by containerd.
  • Layers are content-addressable and shared across images and nodes — a pull only transfers what isn't already cached.
  • A snapshotter (overlayfs by default) assembles shared, read-only layers plus one thin writable layer per container, without copying shared data.
