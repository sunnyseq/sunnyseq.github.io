CRDs and operators

A CustomResourceDefinition doesn't add a feature to Kubernetes — it adds a new type the same watch-and-reconcile machinery from Chapter 1 already knows how to work with. This chapter is that extension point, and the two mechanisms that keep what it creates from leaking or getting stuck.

22.1 A CRD is a schema, registered the same way everything else is

Every object this course has covered — Pods, Deployments, Services — is a built-in type the API server ships knowing about. A CustomResourceDefinition registers a brand-new one at runtime: submit a CRD for Database, and the API server immediately starts accepting, storing, validating and serving Database objects exactly the way it does Pods — kubectl get databases works, RBAC rules can name it, watches can be opened against it, and it gets its own spec and status split, all without a single line of API server code changing. This is the same GVK/GVR addressing from Chapter 2, extended at runtime rather than compiled in.

A CRD, by itself, is inert in exactly the way a NetworkPolicy is inert without a CNI plugin (Chapter 13), or an Ingress is inert without a controller (Chapter 12): it defines a schema and gets you storage, but nothing reconciles a Database object into an actual running database unless something is watching for one. That something is an operator.

22.2 An operator is Chapter 1's loop, pointed at your own resource

Strip away the unfamiliar name and an operator is exactly the reconciliation loop from Chapter 1 and the informer/work-queue machinery from Chapter 4, applied to a CRD instead of a built-in type. It watches Database objects, compares each one's spec (what you asked for) against real, observed state (what actually exists — a StatefulSet, some Secrets, a backup schedule), and reconciles the gap. Nothing about the loop itself is different; what's different is that the "resource" being reconciled is one you defined, and the "real world" it reconciles against might be several other Kubernetes objects, an external cloud API, or both at once.

kind: Database          # your CRD
spec:
  engine: postgres
  version: "16"
  replicas: 3
status:                 # written by your operator, same split as everything else
  phase: Provisioning
  readyReplicas: 1

22.3 Owner references: garbage collection without a controller lifting a finger

An operator reconciling a Database typically creates several other objects underneath it — a StatefulSet, a Service, some Secrets. Deleting the Database object should clean all of those up, and the mechanism for that is not the operator noticing the deletion and manually deleting each child. It's an owner reference: every child object created records the Database's UID as its owner, and a built-in garbage collector controller — generic, with no knowledge of what a Database even is — watches for owner objects disappearing and deletes every object that named it as owner.

Why this is more than a convenience

Because garbage collection is generic and owner-reference-driven, it works identically for every operator that ever gets installed, without any of them writing cleanup code. It's the same pattern Kubernetes itself already uses natively — a ReplicaSet's pods carry an owner reference back to it (which is how deleting a Deployment cascades all the way down to actual pods disappearing), and a Job's pods work the same way. Operators aren't granted a special capability here; they're simply using a mechanism every built-in controller already depends on.

22.4 Finalizers: the opposite problem — cleanup that must happen first

Owner references handle cleanup after deletion. Some resources need cleanup before the object can actually disappear — releasing a cloud load balancer's external IP, taking a final backup, deregistering from an external system. A finalizer is a string on an object's metadata that tells the API server: don't actually remove this object until whoever added this finalizer has removed it themselves.

metadata:
  finalizers:
  - database.example.com/backup-before-delete
  deletionTimestamp: "2025-01-15T10:00:00Z"   # deletion requested...
  # ...but the object stays fully present, watchable, and gettable
  # until the operator finishes its work and removes the finalizer

This is why kubectl delete on an object with a finalizer can appear to hang — the object isn't stuck, it's in a deliberate, visible waiting state: deletionTimestamp is set, but the object remains fully present until every finalizer naming it is removed. A controller that crashes after setting a finalizer but before ever clearing it leaves that object stuck in exactly this state indefinitely — a common, real operational failure mode, and precisely why a finalizer should only ever be added by code that reliably removes it again.

22.6 Lab · watch owner references and finalizers on real objects

Shell · CRDs, garbage collection and stuck finalizers
# Every custom type this cluster's API actually knows about
kubectl get crds

# A ReplicaSet's pods, and the owner reference tying them together -
# built-in Kubernetes using the exact mechanism this chapter describes
kubectl get pod web-abc -o jsonpath='{.metadata.ownerReferences}'

# Delete a Deployment and watch the cascade happen via owner references,
# not via any code the Deployment controller wrote specifically for this
kubectl delete deployment web
kubectl get replicasets,pods -l app=web   # gone, cascaded

# Find an object that's stuck deleting - the classic finalizer symptom
kubectl get namespace stuck-ns -o jsonpath='{.status.phase} {.spec.finalizers}'
kubectl get database orders-db -o jsonpath='{.metadata.deletionTimestamp} {.metadata.finalizers}'

# Only as a last resort, and only once you understand why the finalizer
# never cleared - force-remove a stuck finalizer
kubectl patch database orders-db -p '{"metadata":{"finalizers":[]}}' --type=merge
# this skips whatever cleanup the finalizer existed to guarantee -
# know what you're giving up before running it

# Watch an operator's own reconcile loop react to your CRD directly
kubectl logs -n operator-system deploy/database-operator -f | grep orders-db

Knowledge check

A CustomResourceDefinition for "Database" is installed, but no operator is running. What happens when a Database object is created?

A CRD only registers a schema and gets you storage/API mechanics identical to any built-in type. Whether anything acts on objects of that type is a separate, independent concern — the same interface/implementation split this course has seen repeatedly (CNI, CRI, Ingress controllers).

An operator creates a StatefulSet, a Service, and a Secret while reconciling a Database object, each with an ownerReference pointing to the Database. The Database is then deleted. What deletes the three child objects?

Owner-reference-driven garbage collection is generic infrastructure, not something each operator implements. It's the exact mechanism already responsible for a Deployment's deletion cascading down to its ReplicaSet and pods — an operator author gets it for free by setting owner references correctly.

A kubectl delete on an object with a finalizer appears to hang — the object still shows up in kubectl get minutes later. What is actually happening?

A finalizer is a deliberate block on actual removal, not a bug. The object isn't "stuck" in an error sense — it's precisely and visibly waiting on whoever added the finalizer to finish their cleanup and remove it, which becomes a real operational problem only when that controller never does.

What is the core difference between what owner references and finalizers each guarantee?

The two solve opposite-direction problems: owner references drive garbage collection of dependents once a parent is gone (after), while finalizers block an object's actual removal until some required cleanup work has completed (before). A sophisticated operator often uses both — finalizers for its own pre-delete work, owner references for everything it creates.

22.7 What to carry into Chapter 23

  • A CRD extends the API's schema at runtime — everything about GVK addressing, storage, RBAC and watches works identically to a built-in type from the moment it's registered.
  • An operator is Chapter 1's reconciliation loop and Chapter 4's informer pattern, pointed at a CRD instead of a built-in resource — no new mechanism, just a new target.
  • Owner references drive generic, built-in garbage collection after deletion; this is the same mechanism behind a Deployment's cascade to its pods.
  • Finalizers block actual deletion until required cleanup finishes — visible as a deletionTimestamp with the object still fully present, and a real risk of getting stuck if the responsible controller never clears it.

Every mechanism this course has covered eventually shows up as a symptom in a cluster that isn't behaving — a pod that won't start, a rollout that won't finish, an object that won't delete. The next chapter is a map from that symptom back to its cause.
