The scheduler

A pod with no node assigned is not running anywhere, and nothing about a control loop fixes that on its own. Something has to look at every unscheduled pod and every node's remaining capacity and make exactly one decision: where. That is the scheduler's entire job, and nothing more.

5.1 A controller like any other, with one unusual write

kube-scheduler is not special machinery bolted onto the side of Kubernetes — it is a controller, built the same way as anything from Chapter 4: it watches for Pods with an empty spec.nodeName, decides which node each one should run on, and writes that decision back as a single field. That write, called a binding, is the scheduler's entire output. It does not talk to nodes, does not start containers, and does not know or care what a container runtime is — it answers exactly one question, "which node," and then it is finished with that pod forever.

# Before scheduling
spec:
  nodeName: ""          # unset — this is literally what makes a pod "Pending"

# After the scheduler acts
spec:
  nodeName: "node-7"     # a single field write. That's the whole binding.

Everything downstream of that write — the kubelet on node-7 noticing a pod is now assigned to it and starting containers — is Chapter 7's subject, not the scheduler's. This split is worth holding onto: "my pod won't schedule" and "my pod is scheduled but won't start" are different failure domains with almost no overlapping causes, and conflating them is the single most common misdiagnosis in Chapter 23's debugging trees.

5.2 Filter, then score

For every unscheduled pod, the scheduler runs the same two-phase process against the current list of nodes:

PhaseQuestionOutput
Filter"Could this pod possibly run here?" — a hard yes/no per nodeThe feasible set — every node that survives every filter
Score"How good a fit is this node, relative to the others?" — a number per node, per pluginThe single highest-scoring node in the feasible set wins

Filters are absolute: a node failing even one — insufficient CPU, a port already bound, a taint the pod does not tolerate — is removed from consideration entirely, regardless of how well it scores on everything else. Scoring only ever ranks among nodes that already passed every filter. A node cannot score its way past a failed filter, and a pod is only unschedulable when the feasible set is empty — every node failed at least one filter.

Score here is deliberately simplified to "how much headroom is left after this pod lands" — real kube-scheduler scoring blends several weighted plugins (spreading pods across nodes, balancing resource use, respecting existing affinity rules) but the shape is identical: every plugin returns a per-node number, and they sum before the highest total wins.

5.4 Steering placement: affinity, taints, spread

Filters and scores are not only about raw capacity. Several mechanisms let you or an admission policy steer placement deliberately, and it is worth being precise about which side of filter/score each one lives on.

MechanismFilter or score?What it expresses
Node affinity (requiredDuringScheduling)Filter"This pod may only land on a node matching these labels" — a hard constraint
Node affinity (preferredDuringScheduling)Score"Prefer a node matching these labels" — influences ranking, never excludes
Pod anti-affinityEither, by the same required/preferred split"Don't co-locate with pods matching this selector" — spreads replicas across failure domains
Taints and tolerationsFilterThe node repels pods by default; a toleration is a pod opting in to a specific taint, not a general override
Topology spread constraintsScore (with an optional hard maxSkew as filter)"Keep replica counts even across zones/nodes" — closes the gap affinity alone leaves for N-way even distribution

Taints deserve the closest reading because the direction is easy to get backwards. A taint is applied to a node and repels pods; a toleration is declared on a pod and does not attract it to that node, it only permits it to land there if everything else already selected it. NoSchedule stops new pods from being placed; NoExecute additionally evicts pods already running there that lack the matching toleration. This is the mechanism behind a control-plane node refusing ordinary workloads by default, and behind a node under disk pressure or memory pressure automatically repelling new pods the instant the kubelet marks it tainted — no scheduler-side awareness of "disk pressure" as a concept is needed, only a taint and the same filter logic used for everything else.

5.5 Preemption: making room by force

A pod can be feasible-on-paper but unable to fit because every otherwise-suitable node is already full of lower-priority work. Rather than leaving that pod Pending indefinitely, the scheduler can invoke preemption: find a node where evicting one or more lower-priorityClass pods would make room, evict them, and schedule the higher-priority pod in their place.

Preemption is a last resort, tried only after the normal filter/score pass fails to find room, and it only ever evicts pods with strictly lower priority than the pending one — a pod can never preempt an equal or higher-priority pod, which is what stops the mechanism from becoming a mutual eviction war between pods of the same tier. The evicted pods do not vanish; they go back through the same scheduling loop themselves, Pending until something makes room for them — which is why aggressive high-priority workloads on an undersized cluster can produce a visible cascade of evictions rippling through lower-priority tiers rather than one clean placement.

kubectl get pod web-abc123 -o jsonpath='{.spec.priorityClassName} {.spec.priority}'

# Watch preemption happen live: create a high-priority pod on a full
# cluster and watch a lower-priority one disappear
kubectl get events --field-selector reason=Preempted -w

Knowledge check

A pod stays Pending. kubectl describe pod shows a FailedScheduling event listing reasons for every node. What does this tell you about the scoring phase?

Score only ranks among nodes that already passed every filter. A FailedScheduling event listing per-node filter failures for all nodes means the feasible set was empty — the scheduler never reached the scoring phase because there was nothing left in it to score.

A node is tainted dedicated=gpu:NoSchedule. A pod with no matching toleration is submitted. What happens to a copy of that same pod already running on that node when the taint is first applied?

The two taint effects are distinct on purpose. NoSchedule is a filter applied only at placement time — pods already running are unaffected. NoExecute is the effect that actively evicts non-tolerating pods already present, which is why marking a node NoExecute (as the kubelet does automatically under real disk or memory pressure) has an immediate, visible effect on running workloads.

A high-priority pod triggers preemption, evicting a lower-priority pod to make room. What happens to the evicted pod?

Preemption does not special-case what happens to the loser — it goes back through the exact same filter/score process as any newly-created pod, competing for whatever room exists across the whole cluster. If it too is high enough priority relative to something else, it can cascade into a further preemption rather than simply waiting.

Which statement about node affinity is correct?

The naming is the specification: "required" constraints are evaluated during the filter phase and can legitimately reduce the feasible set to zero, producing Pending. "Preferred" constraints only ever adjust score among nodes that already passed every filter — a node can never be excluded purely for scoring low on a preference.

5.7 What to carry into Chapter 6

  • The scheduler is a controller whose entire output is one field write, spec.nodeName — placement decisions and pod startup are separate concerns handled by separate components.
  • Filter is a hard yes/no per node; score only ranks within nodes that already passed every filter. A node cannot out-score a failed filter.
  • Required affinity, taints without matching tolerations, and insufficient resources are all filters. Preferred affinity and topology spread scoring are not — they shape ranking, not eligibility.
  • NoSchedule and NoExecute are different guarantees: one blocks new placement, the other actively evicts what is already running.
  • Preemption evicts lower-priority pods to make room, then re-queues them through the identical scheduling path — it is not a special code path with its own rules.

The scheduler's write only tells a node "you now own this pod." What happens on that node between that write and a running container — the kubelet's own loop, probes, and every phase a pod moves through — is the next chapter.
