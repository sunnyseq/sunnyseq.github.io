The kubelet

Every reconcile loop this course has described ends, eventually, at one node deciding to actually start a process. That decision belongs to the kubelet, the one component with no failover story of its own, and everything from probing to eviction to the control plane's own bootstrapping runs through its single per-node loop.

7.1 The one component that is not optional

Every control-plane component this course has covered so far — the API server, the scheduler, every controller — can restart, fail over, or briefly disappear without a running workload noticing. The kubelet cannot. It is the node agent: the process on every node responsible for making that node's slice of the cluster's desired state real, and if it stops, nothing on that node is managed by Kubernetes anymore, whether or not the containers themselves keep running.

Structurally the kubelet is a reconciliation loop like any other controller from Chapter 4 — except its "desired state" input is not one GVK watched cluster-wide, it is the set of pods bound to this specific node, and its "act" step does not call the Kubernetes API to create an object, it calls the container runtime (Chapter 8) to actually start and stop processes. It is the hinge between the declarative world every earlier chapter described and real containers running on real hardware.

7.2 Two ways a pod reaches the kubelet

Almost every pod the kubelet manages arrived via the scheduler's binding write from Chapter 5 — the kubelet watches for pods with spec.nodeName set to its own node and reconciles those. But one category bypasses the API server for its desired state entirely: a static pod, defined by a manifest file sitting directly in a directory the kubelet watches on disk, with no scheduler, no API write, involved in creating it at all.

Why this exists

Static pods solve a bootstrapping problem: how do you run the API server itself as a pod, when running any pod normally requires an API server to already be up to schedule it onto a node? kubeadm-based clusters answer this by running the control plane's own components — kube-apiserver, kube-scheduler, kube-controller-manager — as static pods, started directly by the kubelet from local manifest files, before there is a working control plane to ask permission from.

The kubelet still creates a mirror pod in the API server for every static pod it runs, purely so kubectl get pods shows it like anything else — but editing or deleting that mirror object does nothing to the real pod. The only source of truth for a static pod is the file on disk; the mirror is read-only from the API server's side of the relationship, which inverts the direction every other object in this course has followed so far.

7.3 PLEG: watching the runtime without drowning in polls

The kubelet needs to know, promptly, when a container it manages starts, stops, or crashes — not just the ones it told the runtime to start, but any state change at all. Naively, this means listing every container's state on every node continuously, which scales badly as pod density per node grows. The Pod Lifecycle Event Generator (PLEG) is the kubelet's answer: instead of a full poll of every pod on every tick, it periodically relists containers, diffs the result against its own last-known snapshot, and emits an internal event only for what actually changed — a container exited, a container started — which is what actually triggers a reconcile pass for that specific pod, rather than the kubelet's main loop re-scanning everything on every tick regardless of whether anything moved.

This should look familiar: it is the same shape as Chapter 4's shared informer plus work queue, just running one layer lower, against the container runtime's state instead of the API server's. A PLEG that falls behind — the classic symptom is PLEG is not healthy in kubelet logs, usually from an overloaded or slow container runtime — has the same effect a stalled informer has one layer up: the kubelet's view of container state goes stale, and everything downstream of it (status reporting, probe scheduling, restart decisions) lags with it.

7.4 Node status and the heartbeat lease

The kubelet reports two things about its node, on two different cadences, for a deliberate reason. Full NodeStatus — capacity, allocatable resources, conditions like MemoryPressure and DiskPressure, images cached locally — is comparatively large and is only pushed on a slower interval or when something in it actually changes. A separate, tiny Node Lease object (the same Lease primitive from Chapter 3) is renewed on a fast, fixed interval purely to say "I am still alive," with no payload beyond the renewal timestamp itself.

Splitting these apart is a direct scaling decision: heartbeating a lightweight Lease frequently is cheap even across thousands of nodes, while pushing the full, heavier NodeStatus at that same frequency would not be. The node controller watches the Lease for liveness and NodeStatus for everything else, and a node whose Lease stops renewing is what starts the countdown toward that node's pods being marked for eviction — well before a human would notice anything from the outside.

7.5 Watch node pressure evict pods

When a node runs low on a compressible-in-theory-but-not-in-practice resource — memory being the sharp case, since a process cannot be throttled the way CPU can — the kubelet detects pressure locally and starts evicting pods to relieve it, without waiting for the scheduler or any cluster-level component to intervene. Eviction order is not first-in-first-out; it is driven by each pod's Quality of Service class, derived automatically from its resource requests and limits (the full mechanics are Chapter 18's subject — this is the consequence).

Knowledge check

You run kubectl delete pod kube-scheduler-node-1 -n kube-system on a kubeadm cluster and the pod reappears seconds later, unchanged. Why?

Static pods invert the usual direction of control: the API object is a mirror the kubelet creates for visibility, not the thing driving reality. Deleting the mirror doesn't touch the actual desired state, which lives in a file on the node — so the kubelet just runs its normal reconcile and recreates the mirror against the still-running (or freshly restarted) container.

What problem does PLEG solve that a naive "list every container's status every tick" approach does not?

PLEG is the kubelet's version of Chapter 4's informer-plus-queue pattern, applied to the container runtime instead of the API server: relist, diff against the prior snapshot, emit events only for actual changes. This is what keeps the kubelet's reconcile work proportional to what's actually changing rather than to total pod count on every single tick.

Node status (capacity, conditions, images) and the Node Lease are reported on different cadences. Why split them?

This is a straightforward cost-of-frequency tradeoff. A bare timestamp can be renewed often and cheaply at any cluster size; a full status payload with conditions and capacity cannot be pushed at that same frequency without real overhead, so only the minimum needed for liveness detection runs fast, and everything else runs on a slower, event-driven cadence.

A node hits MemoryPressure with one BestEffort, one Burstable, and one Guaranteed pod running. Which does the kubelet evict first?

QoS class is exactly the signal eviction order is built on: BestEffort pods made no resource promises at all and are evicted first, Burstable pods next, and Guaranteed pods are evicted only as an absolute last resort. The kubelet also re-measures pressure after each eviction rather than evicting a fixed batch upfront.

7.7 What to carry into Chapter 8

  • The kubelet is a per-node reconciliation loop whose desired state is "pods bound to this node" and whose action step calls the container runtime directly.
  • Static pods are the one exception to API-server-as-source-of-truth: their manifest lives on disk, and the API object is a read-only mirror.
  • PLEG applies the informer/queue pattern one layer down — diffing runtime state instead of polling it wholesale on every tick.
  • Node status and Node Lease are split by cost: a small, frequent heartbeat for liveness, a larger, less frequent payload for everything else.
  • Eviction under pressure is QoS-ordered and incremental, not proportional to pod size or arbitrary — BestEffort first, Guaranteed last, re-measured after each step.

Every time this chapter said "the kubelet calls the runtime to start a container," it skipped over what that call actually does — the interface it speaks, and the layers of software between "start this container" and a process actually running in its own isolated namespace. That gap is Chapter 8.
