Part I  ·  The model  ·  Chapter 03

etcd

The API server is a facade. Underneath it sits one piece of infrastructure that actually holds the bytes, orders every write into a single global log, and refuses to let the cluster ever disagree with itself about what happened. That is etcd, and its guarantees are the ceiling on everything built above it.

3.1 A cluster is a distributed log, not a database

It is tempting to think of etcd as "the database Kubernetes uses," in the way an application might use Postgres. That framing hides the property that actually matters. etcd is not primarily storing rows you query — it is maintaining a single, globally ordered log of every change ever made to cluster state, and exposing the current value of every key as a side effect of replaying that log. The API server's resourceVersion from Chapter 2 is not a per-object counter etcd invents for convenience; it is a position in that log, called a revision, and it increases by exactly one for every write to the entire cluster, regardless of which key changed.

This single fact — one global, strictly increasing revision counter shared by every object in the cluster — is what makes a watch stream meaningful at all. "Give me everything that changed since revision 4021" is a well-defined request precisely because 4021 names an exact point in one total order, not an approximate moment in wall-clock time across a distributed system where clocks disagree.

3.2 Why three or five, never two or four

etcd tolerates the loss of nodes by requiring agreement from a quorum — a strict majority of the cluster — before any write is considered committed. This is Raft consensus, and the arithmetic behind it explains an operational rule that otherwise looks arbitrary: etcd clusters run with an odd member count, and adding a fourth member to a healthy three-node cluster makes it less fault tolerant, not more.

Going from 3 to 4 buys nothing: quorum climbs from 2 to 3, so you can still only lose one member before the cluster stops accepting writes, and you have simply added a node that has to participate in every round of consensus for no gain. This is why every production guide says "3 or 5," never "let's just add a couple more for safety."

Killing the leader triggers an election: surviving members vote, and whichever gets a majority becomes the new leader — typically within one to a few hundred milliseconds, tunable but not eliminable. Writes block for that window. Kill enough members to break quorum and writes stop entirely, on purpose — the alternative is two leaders disagreeing about what happened, which Raft is specifically designed to make impossible.

3.3 The revision model: everything is an append

etcd stores state as a multi-version key-value store. A write never overwrites a key's history in place — it appends a new revision, and the "current value" of a key is simply the most recent revision that touched it. Deleting a key does not erase its history either; it writes a tombstone revision. This is what makes two things possible that a plain overwrite-in-place store could not do:

  • Consistent reads at a point in time. "What did this object look like at revision 4021" is answerable even after later revisions have been written, as long as that history has not yet been compacted away (3.5).
  • Watch from an exact resume point. A controller's watch connection drops at revision 4021 and reconnects five seconds later at revision 4050 — it asks to resume from 4021 and receives every intervening change, rather than only "the current state," which is exactly the guarantee Chapter 2's watch mechanism depends on to avoid losing events across a reconnect.

3.4 Leases: how Kubernetes expresses "this expires"

Nothing about a plain key-value write expires on its own. etcd adds one primitive on top for that: a lease, a TTL that a client must periodically renew (a "keepalive"), and to which any number of keys can be attached. When the lease's TTL elapses without a renewal, etcd deletes every key attached to it — atomically, as a side effect of the lease itself expiring, not because some external process noticed and cleaned up.

This is the actual mechanism, not an analogy, behind two things that look unrelated on the surface:

FeatureWhat is lease-backed
Node heartbeatsEach Node has an associated Lease object the kubelet renews roughly every 10 seconds. Stop renewing — the kubelet has crashed or lost network — and the lease expires; that expiry is what the node controller treats as "this node has gone unresponsive," well before any human notices.
Leader electionEvery control-plane component that runs in multiple replicas for availability but must have exactly one active leader (the scheduler, the controller-manager, most operators) acquires a Lease. Holding it renewed is being the leader. Crash without releasing it, and the lease simply times out, letting a standby replica take over within seconds — no separate failure-detection protocol required.

Both features are "a Lease with keys attached," reusing the exact same TTL-and-keepalive primitive rather than each inventing its own liveness protocol.

3.5 Compaction: the log cannot grow forever

If every revision of every key is retained permanently, etcd's disk usage grows without bound on a cluster with any write volume at all — and a cluster running dozens of controllers, each reconciling on its own schedule, writes constantly even when nothing user-visible is changing. Compaction is the deliberate, periodic act of discarding history older than a chosen revision, keeping only the current value of each key (plus whatever recent history is still needed to serve in-flight watches). Compaction is not automatic by default in every etcd deployment — kube-apiserver typically configures it — and getting it wrong in either direction has a real failure mode:

The two failure modes

Compact too rarely, or not at all: the underlying database file grows until it hits etcd's storage quota (2 GB by default), and etcd stops accepting writes cluster-wide — a fully self-inflicted outage with no external cause to point at. Compact too aggressively relative to watch activity: a client's watch tries to resume from a revision that has already been compacted away, and etcd returns an explicit "compacted" error rather than silently serving wrong data — forcing that client to fall back to a full re-LIST, which is exactly the re-synchronisation path Chapter 2 described for a dropped watch, just triggered by a different cause.

Compaction reclaims revision history but not disk space by itself — the database file does not shrink until a separate defragmentation pass runs, which is why "etcd disk usage keeps climbing despite compaction being enabled" is its own, distinct operational question from "is compaction running at all."

3.6 Lab · read etcd's fingerprints through the API

You will rarely talk to etcd directly — that is by design, per Chapter 2 — but its behaviour is visible everywhere once you know to look for it.

Shell · revisions, leases and compaction, from outside etcd
# The cluster-wide revision counter, visible as resourceVersion on any object —
# watch it climb even when you touch a totally unrelated object
kubectl get cm any-configmap -o jsonpath='{.metadata.resourceVersion}'
kubectl label pod some-pod touched=yes
kubectl get cm any-configmap -o jsonpath='{.metadata.resourceVersion}'
# usually unchanged — resourceVersion IS the object's own last-write revision,
# not the global counter directly, but both move from the same underlying log

# Node heartbeats — a Lease object, renewed continuously by the kubelet
kubectl get lease -n kube-node-lease
kubectl get lease  -n kube-node-lease -o yaml | grep renewTime

# Leader election in action — watch a controller's Lease change holders
kubectl get lease -n kube-system kube-controller-manager -o yaml \

Knowledge check

A 5-node etcd cluster loses network connectivity to 2 of its members. What happens?

Quorum for 5 members is 3. Losing 2 leaves exactly 3 reachable, which is still a majority — the remaining members can elect a leader and keep committing writes. Losing 3 of 5, dropping the reachable set below quorum, is what would actually halt writes.

Growing a healthy 3-node etcd cluster to 4 nodes, without also planning for 5, does what to its fault tolerance?

Quorum is a strict majority: 2 of 3 and 3 of 4 both tolerate exactly one member failing before quorum is lost. The 4th node adds cost and one more participant in every consensus round without buying any additional tolerated failure — which is exactly why production guidance sticks to odd counts.

A kubelet crashes and never sends another heartbeat. What is the actual mechanism by which Kubernetes notices the node is gone?

Node liveness is a Lease, the same TTL-and-keepalive primitive used for leader election. The kubelet is responsible for renewing it; if it stops, the lease simply expires on its own schedule, and the node controller — watching Lease objects like any other controller — reacts to that expiry. No component actively probes the node.

A controller's watch, resumed from a revision that etcd has since compacted away, receives an explicit "compacted" error instead of a stream of events. What should the controller do?

A compacted-away resume point is etcd correctly refusing to serve a request it cannot fulfil accurately, rather than silently skipping history. It is one more instance of the general rule from Chapters 1 and 2: a watch is never the sole source of truth, and any time it cannot continue cleanly, the correct response is to re-derive current state directly and resume from there.

3.7 What to carry into Chapter 4

  • etcd is a replicated, ordered log first and a key-value store second — resourceVersion is a position in that log, shared globally across every object in the cluster.
  • Raft requires a strict majority (quorum) to commit any write, which is why cluster sizes are odd and why 3→4 buys nothing.
  • Leases are a single TTL-and-keepalive primitive underneath both node heartbeats and leader election — not two separate mechanisms that happen to look similar.
  • Compaction bounds etcd's growth by discarding old revisions; skip it and the cluster eventually refuses all writes on its own, with no external trigger needed.
  • A watch that cannot continue — dropped connection or compacted revision — is handled the same way every time: re-LIST, get fresh state, resume from there.
