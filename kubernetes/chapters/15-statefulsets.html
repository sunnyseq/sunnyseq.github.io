Part IV  ·  Storage and state  ·  Chapter 15

StatefulSets

A ReplicaSet's pods are interchangeable by design — kill one, get a stranger back. Some workloads need the opposite: the same name, the same volume, the same position in line, every time. This chapter is the controller built for exactly that.

15.1 What a Deployment genuinely cannot promise

A Deployment's ReplicaSet (Chapter 16) treats its pods as interchangeable — kill any one of them, and its replacement gets a fresh, unrelated name and, if it's using a volume at all, whatever the pod template happens to specify, with no notion of "this replacement is standing in for that specific instance." That's exactly right for a stateless web server, and exactly wrong for a database replica that needs to rejoin a cluster as the same member it was before, with the same data, the same identity, in the same relative position.

A StatefulSet exists for precisely that gap. It provides three guarantees a Deployment does not: a stable, predictable name per pod that survives rescheduling, a persistent volume that follows that specific identity rather than being handed out generically, and — critically — control over the order pods are created, scaled and terminated in.

15.2 Ordinals: identity as a number, not a hash

Where a ReplicaSet names its pods with a random suffix (web-7f9c4d8b6-x2k9p), a StatefulSet named db with 3 replicas creates exactly db-0, db-1, db-2 — and when db-1 is deleted for any reason, its replacement is created as db-1 again, not some fourth, differently-named pod. The ordinal is the identity. Nothing about which physical node it lands on, or when it was created, changes that name.

StatefulSet "db", replicas: 3
  db-0   ordinal 0   volume: data-db-0
  db-1   ordinal 1   volume: data-db-1
  db-2   ordinal 2   volume: data-db-2

# Delete db-1. Its replacement:
  db-1   ordinal 1   volume: data-db-1   <- same name, same volume, rejoins as itself

15.3 volumeClaimTemplates: a PVC that follows the ordinal, not the pod

A regular pod template's volume references one specific PVC, shared by every replica — clearly wrong here, since db-0 and db-1 must never share a data directory. A StatefulSet instead declares a volumeClaimTemplate: not a PVC itself, but a stamp used to create one per ordinal, the first time that ordinal's pod is created. db-0 gets its own PVC (conventionally named data-db-0), db-1 gets data-db-1, and so on — and deleting and recreating the pod at a given ordinal reuses that same PVC rather than provisioning a new one, which is what makes "the replacement rejoins with the same data" actually true rather than aspirational.

The part that surprises people

Deleting a StatefulSet does not delete the PVCs its volumeClaimTemplates created. This is deliberate — it protects data from an accidental kubectl delete statefulset — but it means scaling a StatefulSet down and back up does not give you fresh volumes; ordinal 2's old data is still sitting there, still bound, waiting for a pod at that ordinal to reclaim it. Genuinely wanting a clean slate means deleting the PVCs explicitly, a separate, deliberate action.

15.4 Ordered, one at a time, and it waits for Ready

By default, a StatefulSet creates pods in strict ascending order — db-0 first, and it must reach Ready (Chapter 6) before db-1 is even created, and so on. Scaling down reverses the order: the highest ordinal terminates first, and termination of one must complete before the next one down begins. This is the opposite of a ReplicaSet, which creates and destroys pods with no ordering guarantee at all, in parallel, as fast as it can.

15.5 The headless Service underneath: identity you can actually address

A StatefulSet is always paired with a headless Service (Chapter 11 — clusterIP: None), and this is not incidental plumbing. Because DNS for a headless Service resolves to individual pod IPs rather than one load-balanced address, and because each StatefulSet pod's hostname is set to its ordinal name, every replica gets its own stable, individually addressable DNS name: db-0.db.default.svc.cluster.local always resolves to whichever pod currently holds the db-0 identity, not to "some replica, load-balanced." That is what lets a client — or the replicas themselves — talk to a specific member, which is the entire point for anything doing peer discovery, primary election, or ordered replication.

15.6 Lab · watch ordinals, PVCs and per-pod DNS hold together

Shell · stable identity, made concrete
# Ordinal-named pods, in order
kubectl get pods -l app=db -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName

# The PVC created per ordinal - note the naming convention
kubectl get pvc -l app=db
#   data-db-0   Bound   ...
#   data-db-1   Bound   ...

# Prove the PVC survives a pod's deletion and is reused, not recreated
kubectl delete pod db-1
kubectl get pvc data-db-1 -o jsonpath='{.metadata.uid}'   # compare before/after - unchanged

# Prove deleting the whole StatefulSet doesn't touch the PVCs
kubectl delete statefulset db
kubectl get pvc -l app=db   # still there, still Bound

# Per-pod DNS - a specific replica, not a load-balanced pick
kubectl exec -it debug-pod -- nslookup db-0.db.default.svc.cluster.local
kubectl exec -it debug-pod -- nslookup db-1.db.default.svc.cluster.local

# Watch ordered rollout for yourself
kubectl scale statefulset db --replicas=5
kubectl get pods -l app=db -w   # db-3 Running/Ready before db-4 even appears

Knowledge check

A StatefulSet's pod db-1 is deleted (not the whole StatefulSet). What identity does its replacement get?

The ordinal is the pod's stable identity, maintained by the StatefulSet controller regardless of why a given pod disappeared. The replacement is created specifically to fill the db-1 slot again, reusing the same volumeClaimTemplate-derived PVC and the same DNS name — that continuity is the entire feature.

A StatefulSet with 3 replicas is deleted entirely with kubectl delete statefulset. What happens to its PVCs?

This is a deliberate safety property, not an oversight: volumeClaimTemplate-created PVCs outlive the StatefulSet that created them. Recreating the StatefulSet with the same name reunites each ordinal with its original PVC — reclaiming the data is possible precisely because nothing deleted it in the first place.

A StatefulSet is scaled from 1 to 3 replicas. What is true about the creation of db-1 and db-2?

Ordered, sequential rollout — gated on readiness, not just creation — is one of the three core guarantees a StatefulSet adds over a ReplicaSet. This matters concretely for anything where a later replica's startup depends on an earlier one already being a healthy, joinable cluster member.

Why is a StatefulSet always paired with a headless Service rather than a normal ClusterIP Service?

The whole value of ordinal identity would be lost if clients could only ever reach "some replica" through a load-balanced ClusterIP. A headless Service is what turns "db-1 exists as a stable identity" into "db-1.db.default.svc.cluster.local reliably reaches that specific pod," which is what peer-aware, ordered systems actually need.

15.7 What to carry into Chapter 16

  • A StatefulSet adds exactly what a Deployment doesn't need and doesn't provide: stable per-ordinal identity, a persistent volume that follows that identity, and strict creation/termination ordering.
  • volumeClaimTemplates stamp out one PVC per ordinal on first creation, then reuse it — a pod's replacement reclaims its predecessor's data, not a fresh volume.
  • Deleting a StatefulSet does not delete its PVCs, by design — a safety property, not a gap.
  • A paired headless Service is what makes ordinal identity actually reachable, via stable per-pod DNS names rather than a load-balanced pick.
