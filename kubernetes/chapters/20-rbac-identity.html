RBAC and workload identity

RBAC answers exactly one question — is this identity allowed to do this, to this, here — and nothing about how that identity proved itself. This chapter is that question, the two-object grant it's built from, and the identity a pod actually carries, which is never yours.

20.1 Three questions, and RBAC only answers one

Chapter 2's request path named three separate questions the API server asks of every request: who are you (authentication), are you allowed (authorization), and is this well-formed (admission/validation). RBAC lives entirely in the second question. It has no opinion about how a request proved its identity — a client certificate, a bearer token, an OIDC ID token are all equally acceptable inputs to RBAC, which only ever sees the output of authentication: a username and a set of group memberships. Everything RBAC decides is a pure function of (user or group, verb, resource, namespace) — nothing about the request body, nothing about time of day, nothing about where the request came from.

20.2 Role and RoleBinding: a grant is two objects, never one

Permission in RBAC is always expressed as two separate objects, deliberately kept apart: a Role (or ClusterRole) lists what is allowed — verbs against resources — with no mention of who; a RoleBinding (or ClusterRoleBinding) names who gets a specific Role, with no mention of what it permits. Neither object does anything alone.

Role "pod-reader" (namespace: default)        RoleBinding "read-pods-as-alice"
  rules:                                         subjects:
  - apiGroups: [""]                              - kind: User
    resources: ["pods"]                             name: alice
    verbs: ["get", "list", "watch"]              roleRef:
                                                    kind: Role
                                                    name: pod-reader

The split matters operationally: the same Role can be bound to many different subjects via many separate RoleBindings without editing the Role at all, and revoking one person's access is deleting one RoleBinding, never touching the permission definition itself. Four combinations exist, distinguished by whether the permission-listing object and the binding are namespaced or cluster-scoped:

CombinationScope of the grant
Role + RoleBindingOne namespace only
ClusterRole + RoleBindingOne namespace, but reusing a permission set defined once, cluster-wide (a common pattern: define "view" once as a ClusterRole, bind it namespace-by-namespace)
ClusterRole + ClusterRoleBindingEvery namespace, cluster-wide
Role + ClusterRoleBindingNot valid — a namespaced Role cannot be referenced by a cluster-scoped binding

RBAC is default-deny with no exceptions — there is no rule that explicitly forbids something, only the absence of a rule that allows it. "Not permitted" and "no matching rule exists" are the same outcome, always.

20.4 A pod's identity is not your identity

Every pod authenticates to the API server as a ServiceAccount — never as the human who created it. A pod created by alice and a pod created by bob, both using the same ServiceAccount, present the exact same identity to the API server; RBAC has no memory of who applied the manifest, only of which ServiceAccount the running pod is using right now. This is precisely why granting a ServiceAccount broad permissions "just for this one job" is a durable decision, not a temporary one — every future pod that mounts that ServiceAccount inherits it, indefinitely, regardless of who deploys it.

The default ServiceAccount is not a safe default

Every namespace has a default ServiceAccount, and every pod that doesn't specify one uses it automatically. On many clusters, that account can read a wide range of objects in its namespace by virtue of whatever's bound to it — and a single vulnerable, internet-facing pod with the default ServiceAccount's token mounted is a real, common path to lateral movement inside a cluster. Explicitly creating a dedicated, minimally-scoped ServiceAccount per workload — and setting automountServiceAccountToken: false on anything that doesn't need to talk to the API server at all — is not a hardening nicety, it's closing a door that's open by default.

20.5 Bound, projected, and expiring — not the old long-lived token

Early Kubernetes mounted a ServiceAccount's token as a static Secret, valid forever, with no expiry and no way to tell whether a given copy was ever actually revoked. Modern clusters use bound service account tokens instead, projected into the pod as a volume and refreshed automatically well before they expire (typically within an hour). The improvement is not just a shorter lifetime — a bound token is cryptographically tied to the specific pod (and optionally a specific audience, like a particular external service it's meant to authenticate to), so a token stolen from one pod's filesystem cannot be replayed indefinitely, nor used to impersonate a different pod, and it stops being valid the moment the pod it was issued for is deleted.

20.6 Lab · trace a permission from binding to decision

Shell · RBAC, service accounts, and token projection
# The single most useful RBAC command that exists - ask, don't guess
kubectl auth can-i delete pods --as=alice -n default
kubectl auth can-i create deployments --as=system:serviceaccount:ci:deployer

# Every RoleBinding actually granting a given subject anything, cluster-wide
kubectl get rolebindings,clusterrolebindings -A -o json \
  | jq '.items[] | select(.subjects[]?.name=="alice")'

# What ServiceAccount is this pod actually running as, and what can it do
kubectl get pod web-abc -o jsonpath='{.spec.serviceAccountName}'
kubectl auth can-i --list --as=system:serviceaccount:default:web-sa

# Confirm the default ServiceAccount's actual blast radius before assuming it's harmless
kubectl auth can-i --list --as=system:serviceaccount:default:default

# The projected, bound token itself - short-lived, audience-scoped
kubectl exec web-abc -- cat /var/run/secrets/kubernetes.io/serviceaccount/token | cut -d. -f2 | base64 -d
#   {"aud":["https://kubernetes.default.svc"],"exp":..., "sub":"system:serviceaccount:default:web-sa"}

# Turn off auto-mounting for a pod that never talks to the API server
kubectl patch serviceaccount web-sa -p '{"automountServiceAccountToken": false}'

Knowledge check

A Role grants get/list/watch on pods, but no RoleBinding exists connecting it to any subject. What can that Role actually do?

Roles and RoleBindings are deliberately separate and both required. A Role by itself is just a named list of rules sitting inert — it confers nothing until a RoleBinding (or ClusterRoleBinding) actually connects it to a subject.

Two different humans, alice and bob, both create pods that use the same ServiceAccount "shared-sa". How does the API server tell their pods' requests apart for RBAC purposes?

A pod's RBAC identity is entirely its ServiceAccount, with no memory of who applied the manifest that created it. Two pods sharing a ServiceAccount are, from RBAC's perspective, indistinguishable — which is exactly why scoping ServiceAccounts narrowly per workload matters more than it might seem.

What is the concrete security improvement of a bound, projected service account token over the old static Secret-based token?

The old static token had no expiry and no binding to the pod using it — once copied, it worked forever, from anywhere. A bound token's short lifetime and pod-specific binding sharply limits what a single stolen token can actually be used for, and for how long.

A pod is deployed with no serviceAccountName specified. What identity does it authenticate to the API server as?

Every namespace's default ServiceAccount is used automatically for any pod that doesn't specify one, and it is mounted by default too. On clusters where that account has any real permissions bound to it, every such pod inherits them — which is precisely why it isn't a safe default to leave alone.

20.7 What to carry into Chapter 21

  • RBAC answers exactly one question — is this (user or group, verb, resource, namespace) combination allowed — and is entirely default-deny with no explicit-deny concept.
  • A Role/ClusterRole lists permissions; a RoleBinding/ClusterRoleBinding grants them to a subject; neither does anything alone, and the four combinations differ in scope, not mechanism.
  • A pod's identity is its ServiceAccount, never the human who created it — RBAC cannot see past that boundary.
  • Bound, projected tokens replaced long-lived static ones specifically to bound how long and how widely a stolen token stays useful.
