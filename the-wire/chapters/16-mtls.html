Part IV  ·  TLS on the wire  ·  Chapter 16

Mutual TLS

Ordinary TLS authenticates one party. The client learns it is talking to the right server and the server has no idea who the client is — it finds out later, at the application layer, from a password or a token. mTLS moves that proof into the handshake, and the consequences are larger than they first appear.

16.1 The asymmetry in normal TLS

Everything in Part IV so far has been one-directional. The server proves key possession by signing the transcript; the client proves nothing. That is the right default for the web — requiring every visitor to hold a certificate would be unworkable — but it means the connection carries no notion of who is calling.

So authentication happens afterwards, in the application: a session cookie, a bearer token, an API key. All of these share a property that matters enormously: they are secrets that travel, so anyone who obtains a copy can use it. A leaked token in a log file, a stolen cookie, an API key committed to a repository — each is directly replayable by whoever finds it.

A client certificate is different in kind. The private key never moves. What travels is a signature over this specific handshake transcript, which is worthless on any other connection.

Interactive · one-way versus mutualServer authentication only
The distinction that matters: a bearer token is a secret that travels, so a copy is as good as the original. A certificate proves possession of a key that never travels, so a copy of the certificate alone is useless.

16.2 What changes in the handshake

Three messages appear, and one of them is the one that matters.

TLS 1.3 with client authentication:

Client                                          Server
ClientHello + key_share      -------->
                                            ServerHello
                                   {EncryptedExtensions}
                                   {CertificateRequest}   <-- 1. server asks
                                           {Certificate}
                                     {CertificateVerify}
                             <--------      {Finished}
{Certificate}                                              <-- 2. client's chain
{CertificateVerify}                                        <-- 3. THE PROOF
{Finished}                   -------->
[Application Data]           <------->  [Application Data]
  • CertificateRequest — the server asks, optionally naming acceptable CAs so the client can pick the right certificate from several.
  • Certificate — the client's chain. Public information; on its own it proves nothing.
  • CertificateVerify — a signature over the transcript hash with the client's private key. This is the authentication. It proves the client holds the key, and binds that proof to this connection.

The server then runs full path validation from Chapter 8 — signatures, validity, basicConstraints, revocation — plus an identity check appropriate to its own policy. In TLS 1.3 all of this is encrypted, so the client's identity is not visible to an observer. In TLS 1.2 the client certificate travelled in cleartext, which was a meaningful privacy problem.

16.3 Where mTLS belongs, and where it does not

ContextVerdictWhy
Service-to-service inside a clusterExcellentMachines, automated rotation, a private CA you control
API clients — partner integrationsGoodSmall, known population; far stronger than a shared API key
Device fleets — IoT, kiosksGoodIdentity provisioned once at manufacture, keys in a secure element
Admin access to infrastructureGoodSmall population, high value, non-phishable
Consumer web loginPoorEnrolment, device loss, and key portability are unsolvable at that scale — passkeys solve the same problem better (Ch. 19)
Why mTLS is not phishable

A phishing site can capture a password or a one-time code because the user hands them over. It cannot capture a client certificate authentication, because the private key never leaves the machine and the signature is over a transcript belonging to that specific TLS connection. A signature captured on the phishing site's connection is meaningless on the real one. WebAuthn and passkeys use exactly this property, applied at the application layer with better ergonomics — which is why they, rather than client certificates, became the consumer answer.

16.4 Identity in a service mesh

Inside a cluster the identity you want is not a hostname. It is which workload is calling — which service account, in which namespace, in which cluster. SPIFFE encodes that as a URI in the SAN:

SAN: URI:spiffe://prod.cluster.local/ns/payments/sa/api-server
Issuer: mesh intermediate CA
Validity: 24 hours
Key: generated in the pod, never written to disk, never transmitted

The control plane issues these automatically and rotates them continuously. Several things follow:

  • Revocation stops mattering. At a 24-hour lifetime a stolen key is worthless within a day, which is a stronger practical guarantee than any CRL or OCSP deployment achieves (Ch. 11).
  • Authorisation gets a real subject. Policies say "the payments service may call the ledger service" rather than "this IP range may reach this port." IPs are recycled and reassigned; a workload identity is not.
  • The network stops being a trust boundary. This is the substance behind Zero Trust — Chapter 1's TB-2 boundary gets an actual control instead of an assumption.

The trade-offs, stated honestly

mTLS in a mesh is usually implemented by sidecar proxies intercepting all traffic, and that is not free. Every hop costs latency, every pod costs memory and CPU, and the control plane becomes critical infrastructure — if certificate issuance fails, your services stop talking to each other. Ambient or node-level modes reduce the per-pod cost at the price of coarser identity. The security case is strong; the operational case needs to be made on its own merits.

16.5 The failure modes

Four things that go wrong
  • Optional client auth that silently becomes no auth. Many servers offer a mode where a client certificate is requested but not required. If the application then does not check whether one was actually presented and verified, anyone connects unauthenticated. Verify the result, not the configuration.
  • Certificate expiry taking down a fleet. Short lifetimes are a security win and an availability risk. If issuance is unavailable when certificates expire, everything stops simultaneously. Alert on renewal failures well before expiry, not on expiry itself.
  • Trusting the wrong CA. A server configured to accept any certificate from the public trust store will accept a certificate anyone can buy for a domain they own. The client trust store for mTLS must contain only your issuing CA.
  • Terminating mTLS at the edge and forgetting the rest. If a load balancer verifies the client certificate and then forwards plain HTTP with an X-Client-CN header, anything that can reach the backend directly can forge that header. This is Chapter 1's TB-2 exactly.

16.6 Lab

Shell · build a working mTLS setup
# A private CA (Ch. 8), then a server and a client certificate from it
openssl req -x509 -newkey rsa:4096 -sha256 -days 3650 -nodes \
  -keyout ca.key -out ca.crt -subj "/CN=Field Notes mTLS CA" \
  -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign"

# Server cert \u2014 note extendedKeyUsage=serverAuth
openssl req -newkey rsa:2048 -nodes -keyout srv.key -out srv.csr -subj "/CN=localhost"
openssl x509 -req -in srv.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 90 -sha256 \
  -extfile <(printf "basicConstraints=critical,CA:FALSE\nextendedKeyUsage=serverAuth\nsubjectAltName=DNS:localhost") \
  -out srv.crt

# Client cert \u2014 clientAuth, and a SPIFFE-style workload identity in the SAN
openssl req -newkey rsa:2048 -nodes -keyout cli.key -out cli.csr -subj "/CN=api-server"
openssl x509 -req -in cli.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 1 -sha256 \
  -extfile <(printf "basicConstraints=critical,CA:FALSE\nextendedKeyUsage=clientAuth\nsubjectAltName=URI:spiffe://cluster.local/ns/payments/sa/api-server") \
  -out cli.crt

# Run a server that REQUIRES a client certificate
openssl s_server -accept 8443 -cert srv.crt -key srv.key \
  -CAfile ca.crt -Verify 1 -www &
#   -Verify (capital V) = require.  -verify (lowercase) = request but allow without.
#   That single letter is the difference between enforced and optional.

# Connect WITHOUT a client certificate \u2014 rejected
openssl s_client -connect localhost:8443 -CAfile ca.crt </dev/null 2>&1 \
  | grep -iE 'alert|handshake failure|peer did not return'

# Connect WITH one \u2014 succeeds
openssl s_client -connect localhost:8443 -CAfile ca.crt \
  -cert cli.crt -key cli.key </dev/null 2>/dev/null \
  | grep -E 'Verify return code|Protocol|Cipher'

# See the client identity the server extracted
openssl x509 -in cli.crt -noout -subject -ext subjectAltName,extendedKeyUsage

# curl with a client certificate
curl -v --cacert ca.crt --cert cli.crt --key cli.key https://localhost:8443/ 2>&1 | head -20

# Prove the certificate FILE alone is not enough \u2014 no private key, no auth
curl --cacert ca.crt --cert cli.crt https://localhost:8443/ 2>&1 | tail -2

kill %1 2>/dev/null

Knowledge check

Which message actually authenticates the client in mTLS?

Certificates are public; presenting one proves nothing, exactly as for the server in Chapter 12. CertificateVerify signs the transcript hash, which only the private key holder can do, and binds the proof to this specific connection so it cannot be replayed elsewhere.

An attacker steals a client certificate file from a backup. What can they do?

This is the structural advantage over bearer tokens. A certificate is published on the wire in every handshake. The private key is what matters, and it never travels — which is why a stolen certificate file is inert, and a stolen token is immediately usable.

Why is mTLS unsuitable for consumer web login?

The cryptography is excellent — that is exactly why passkeys borrowed the model. What fails is the human side: getting a certificate onto every device, recovering when a phone is lost, and moving identity between devices. Passkeys solve the same problem at the application layer with usable enrolment and recovery.

A load balancer verifies client certificates and forwards requests to backends over plain HTTP with an X-Client-CN header. What is wrong?

Chapter 1's TB-2 boundary. The header is only trustworthy if the backend is genuinely unreachable except through the edge — and "it's inside the VPC" is the assumption Zero Trust exists to reject. Either re-encrypt with mTLS to the backend, or enforce network policy so only the edge can connect, and always strip any inbound copy of the header at the edge.

16.7 Carry forward

  • CertificateVerify is the authentication. The certificate is just public identity material.
  • Certificates beat bearer tokens because the secret never travels and the proof is bound to one connection.
  • mTLS suits machines and small known populations, not consumer login.
  • In a mesh, identity is the workload, lifetimes are hours, and revocation stops being a problem.
  • "Requested but not required" is the most common silent failure. Verify the outcome, not the config.
  • Terminating mTLS at the edge and trusting a header behind it recreates the problem you just solved.
