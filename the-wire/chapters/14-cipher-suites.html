Cipher suites decoded

A cipher suite name looks like line noise and is actually a complete specification of a connection's cryptography. Once you can read one, a scanner report stops being a list of strings and becomes a description of exactly which primitives from Part II are in play — and which ones you should be worried about.

14.1 Reading the name

TLS 1.2 suite names encode four decisions. TLS 1.3 encodes two, because it made the other two non-negotiable.

14.2 The full anatomy

TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
 |    |     |        |   |   |   |
 |    |     |        |   |   |   +-- PRF/HKDF hash (Ch. 3, 13)
 |    |     |        |   |   +------ mode: GCM is AEAD (Ch. 4)
 |    |     |        |   +---------- key size in bits
 |    |     |        +-------------- bulk cipher (Ch. 4)
 |    |     +----------------------- authentication: cert key type (Ch. 7)
 |    +----------------------------- key exchange (Ch. 6)
 +---------------------------------- protocol

TLS 1.3 collapses this:

TLS_AES_128_GCM_SHA256
 |    |   |   |   |
 |    |   |   |   +-- HKDF hash
 |    |   |   +------ AEAD mode
 |    |   +---------- key size
 |    +-------------- bulk cipher
 +------------------- protocol

  Key exchange and authentication are gone from the name because
  they are negotiated separately, in the supported_groups and
  signature_algorithms extensions. Only ephemeral exchange and
  only AEAD are permitted, so there is nothing left to encode.
A consequence worth knowing

Because TLS 1.3 suites do not name a key exchange or authentication method, the same five suites work with RSA certificates, ECDSA certificates, Ed25519 certificates and PSK resumption. Configuration got dramatically simpler: the old advice to hand-curate a long OpenSSL cipher string is largely obsolete. For 1.3 the correct configuration is to leave the defaults alone. For 1.2, the useful work is removing things, not adding them.

14.3 Negotiation, and who chooses

The client sends an ordered list; the server picks one. Which order wins is a server setting, and it matters:

  • Server preference — the server walks its own ordered list and takes the first the client also supports. Historically recommended, because clients could not be trusted to prefer strong suites.
  • Client preference — the server honours the client's order. Now often better, because modern clients pick correctly for their own hardware: a phone without AES acceleration will prefer ChaCha20, and forcing AES-GCM on it makes it slower for no security gain.

The negotiation happens in cleartext and is therefore rewritable, which is why the Finished transcript MAC (Ch. 12) exists. Two further defences sit alongside it:

  • TLS_FALLBACK_SCSV — a pseudo-suite meaning "this is a retry at a lower version". A server supporting a higher version that sees it knows the downgrade was forced and aborts. This was the response to POODLE.
  • Downgrade sentinels — TLS 1.3 servers that negotiate 1.2 or lower place a known 8-byte value at the end of server_random. A 1.3-capable client seeing it knows something interfered, and fails.

14.4 The extensions that matter

SNI — Server Name Indication

One IP address, many sites. The server must choose a certificate before it can send one, and the only way it knows which is the client telling it — in the ClientHello, before any keys exist. So the hostname you are visiting travels in cleartext on every single connection.

This is the largest metadata leak in TLS, and it is used at scale: national filtering systems block by SNI, corporate proxies log by SNI, and network operators categorise traffic by SNI. Encrypting the rest of the handshake in TLS 1.3 made the gap more conspicuous rather than smaller.

ALPN — Application-Layer Protocol Negotiation

Which protocol runs inside the tunnel — h2, http/1.1, h3 — agreed during the handshake rather than after it, saving a round trip. HTTP/2 over TLS requires it. It is also how a single port serves multiple protocols, and how the TLS-ALPN-01 ACME challenge (Ch. 10) works: a value of acme-tls/1 triggers the validation certificate instead of the real one.

ECH — Encrypted Client Hello

The fix for SNI, and the interesting part is how it escapes the chicken-and-egg problem. The server operator publishes an HPKE public key in DNS, in an HTTPS resource record. The client fetches it — over DoH, so the lookup itself is not observable — and sends two ClientHellos:

  • An outer ClientHello with an innocuous SNI, typically the shared provider's name, such as cloudflare-ech.com.
  • An inner ClientHello, encrypted to the published key, carrying the real SNI and any other sensitive extensions.

An observer sees a connection to a large provider and cannot tell which of the millions of sites behind it you reached. The anonymity set is every site sharing that ECH configuration, which is exactly why ECH works best on large shared infrastructure and gives little on a dedicated IP serving one domain.

What ECH does not hide

The destination IP address is still visible, so on a dedicated host it identifies the site regardless. Traffic volume and timing still leak, and page fingerprinting from sizes alone remains effective. ECH also depends on encrypted DNS — if the client resolves the HTTPS record over plain DNS, the observer learns the hostname there instead and ECH has moved the leak rather than closed it. Its predecessor ESNI was withdrawn partly because it encrypted only the SNI field, leaving other extensions to fingerprint against; ECH encrypts the whole inner ClientHello for that reason.

GREASE

A small idea with a large purpose. Clients deliberately advertise reserved, meaningless values in extension and cipher-suite lists. A correct implementation ignores unknown values; a brittle middlebox chokes. By poisoning the well continuously, GREASE ensures intolerant implementations break immediately and visibly rather than three years later when a real new value appears. It is a direct response to the ossification that shaped TLS 1.3's wire format (Ch. 13).

ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:

14.6 Lab

Shell · read and audit suites
# Decode a suite name into its parts
openssl ciphers -V 'ECDHE-RSA-AES128-GCM-SHA256'
#   0xC0,0x2F - ECDHE-RSA-AES128-GCM-SHA256  TLSv1.2 Kx=ECDH Au=RSA Enc=AESGCM(128) Mac=AEAD
#   Kx = key exchange, Au = authentication, Enc = bulk cipher, Mac = AEAD means no separate MAC

# Everything your OpenSSL supports, with the parts broken out
openssl ciphers -V 'ALL:COMPLEMENTOFALL' | head -30

# Suites that would be a problem, and whether you offer any
openssl ciphers -V 'kRSA'          # static RSA: no forward secrecy
openssl ciphers -V 'SHA1:MD5'      # legacy MAC
openssl ciphers -V 'CBC'           # padding-oracle family
openssl ciphers -V 'NULL:EXPORT:LOW:aNULL:eNULL' 2>/dev/null | head

# What a server actually negotiates, and what it will accept at all
openssl s_client -connect example.com:443 </dev/null 2>/dev/null | grep -E 'Protocol|Cipher'
nmap --script ssl-enum-ciphers -p 443 example.com 2>/dev/null | sed -n '/TLSv1/,/least strength/p'

# Does the server honour client order or impose its own?
openssl s_client -connect example.com:443 -tls1_2 \
  -cipher 'ECDHE-RSA-AES256-GCM-SHA384:ECDHE-RSA-AES128-GCM-SHA256' </dev/null 2>/dev/null | grep Cipher
openssl s_client -connect example.com:443 -tls1_2 \
  -cipher 'ECDHE-RSA-AES128-GCM-SHA256:ECDHE-RSA-AES256-GCM-SHA384' </dev/null 2>/dev/null | grep Cipher
#   Same result both times = server preference. Different = client preference.

# SNI in the clear \u2014 see it for yourself
sudo tcpdump -i any -n -A 'tcp port 443 and tcp[((tcp[12:1] & 0xf0) >> 2):1] = 0x16' -c 2 \
  2>/dev/null | grep -a -o 'example\.com'

# Prove SNI selects the certificate
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject
openssl s_client -connect example.com:443 -servername wrong.example </dev/null 2>/dev/null \
  | openssl x509 -noout -subject     # often a different, default certificate

# ALPN negotiation
openssl s_client -connect example.com:443 -alpn h2,http/1.1 </dev/null 2>/dev/null | grep -i alpn

# Is ECH published for a domain? Look for the HTTPS RR with an ech= parameter
dig +short HTTPS cloudflare.com
dig +short HTTPS crypto.cloudflare.com

Knowledge check

Why do TLS 1.3 cipher suite names omit the key exchange and authentication method?

There is nothing left to encode. Static RSA is gone, non-AEAD suites are gone, and the group and signature algorithm moved into supported_groups and signature_algorithms. One consequence is that the same five suites work with any certificate type.

A server negotiates TLS_RSA_WITH_AES_128_CBC_SHA. What are the two problems?

Two independent failures. TLS_RSA means the client encrypts the premaster secret to the long-term key, so one key compromise decrypts all recorded sessions. CBC_SHA means MAC-then-encrypt with padding, the construction behind Vaudenay's padding oracle and Lucky 13. AES-128 and SHA-1-as-a-MAC are both fine here; the problems are the mode and the exchange.

What does Encrypted Client Hello actually hide, and from whom?

ECH encrypts the inner ClientHello to a key published in DNS, leaving an innocuous outer SNI. The IP address, sizes and timing all still leak, so the protection is only as strong as the anonymity set behind that IP — which is why it works on large shared infrastructure and gives little on a dedicated host. It also requires encrypted DNS, or the hostname leaks in the lookup instead.

What is GREASE for?

Implementations that reject unknown values are the ossification problem — they make a protocol unextendable. GREASE keeps unknown values continuously present in real traffic, so anything intolerant fails during development rather than blocking a future protocol change across the whole internet.

14.7 Carry forward

  • A 1.2 suite name specifies key exchange, authentication, bulk cipher and hash. A 1.3 name specifies only the last two.
  • For 1.2, configuration means removing static RSA and CBC. For 1.3, leave the defaults.
  • Negotiation is cleartext and rewritable, protected retroactively by the Finished transcript MAC plus fallback signalling.
  • SNI is cleartext by design and is the protocol's largest metadata leak.
  • ECH closes it by encrypting the inner ClientHello, and is only as good as the anonymity set behind the IP.
  • GREASE keeps the protocol extensible by breaking brittle implementations on purpose.

The handshake is complete and keys are established. Chapter 15 covers what happens for the rest of the connection's life.
