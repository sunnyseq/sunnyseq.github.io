22.2 Certificates, automated end to end

Two certificate lifecycles run simultaneously in a typical cluster, and they should not be confused:

Ingress certificatesMesh workload certificates
IdentityA public hostnameA SPIFFE URI — namespace, service account (Ch. 16)
Issued byA public CA via ACME (Ch. 10)The mesh's own private CA
LifetimeWeeks, shrinking toward daysHours
Operatorcert-manager, or the cloud load balancer's managed certsIstio, Linkerd, or the platform's mesh control plane
Trust anchorPublic trust stores (Ch. 8)Only other workloads in the mesh

cert-manager is the Kubernetes-native pattern worth understanding in detail, because it turns Chapter 10's ACME flow into a Kubernetes resource:

apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: api-tls
spec:
  secretName: api-tls-secret        # the issued cert lands here as a Secret
  dnsNames: [api.example.com]
  issuerRef: { name: letsencrypt-prod, kind: ClusterIssuer }

---
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: { name: letsencrypt-prod }
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    solvers:
      - dns01: { route53: { region: ap-south-1 } }   # Ch. 10's DNS-01 challenge

A Certificate object is a declarative request; cert-manager runs the ACME protocol, solves the challenge, and writes the result into a Kubernetes Secret — then repeats before expiry, automatically, without a human touching a renewal date. This is the specific mechanism that makes short certificate lifetimes (Ch. 10) operationally sustainable rather than a maintenance burden nobody can keep up with.

Where mesh certificates come from

The mesh control plane runs its own CA — typically an intermediate signed by an operator-controlled root, following Chapter 8's structure exactly. Each sidecar or ztunnel requests a certificate on startup, presenting its Kubernetes service account token as proof of identity; the control plane verifies that token against the API server and issues a SPIFFE certificate scoped to that exact workload. Rotation happens continuously, in the background, invisible to the application. This is Chapter 16's "identity is the workload" made concrete: the certificate is issued because Kubernetes already knows what this pod is.

22.3 Network policy, enforced

By default, every pod in a cluster can reach every other pod. Chapter 20's stateful firewall concept, applied at the pod level, is what closes this:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: api-allow-from-gateway }
spec:
  podSelector: { matchLabels: { app: api } }
  policyTypes: [Ingress, Egress]
  ingress:
    - from: [{ podSelector: { matchLabels: { app: gateway } } }]
      ports: [{ port: 8443 }]
  egress:
    - to: [{ podSelector: { matchLabels: { app: database } } }]
      ports: [{ port: 5432 }]
    # everything else is implicitly denied once ANY policy selects this pod

The critical, frequently-missed detail: a NetworkPolicy is additive and default-deny only once something selects the pod. A pod matched by zero policies is fully open. A pod matched by one ingress-only policy has its egress completely unrestricted, because nothing said otherwise. This is exactly the "deny by default, only where you remembered to write a rule" trap Chapter 20 warned about with topology-based trust.

Enforcement is not a Kubernetes API-server feature — it happens in the CNI, often via eBPF (Ch. 20's link between the network layer and what actually runs in-kernel). A cluster with no policy-enforcing CNI silently accepts these objects and enforces nothing, which is a genuinely dangerous silent failure to check for.

22.5 Workload identity for cloud APIs



Applications need to call cloud provider APIs — read a secret, write to object storage — and the old pattern was a long-lived static credential baked into a Secret. The modern pattern eliminates that credential entirely, using the same federation shape as OIDC (Ch. 19):



1. Kubernetes issues the pod a bound, audience-scoped, short-lived
   service account token (a JWT, signed by the cluster) \u2014 not a secret
   anyone had to generate or store.

2. The pod presents that token to the cloud provider's STS endpoint.

3. The cloud provider validates the token's signature against
   Kubernetes' published OIDC discovery document and JWKS (Ch. 19) \u2014
   confirming it was genuinely issued by this cluster, to this
   specific service account.

4. The cloud provider returns temporary cloud credentials, scoped by
   an IAM trust policy to exactly what that service account may do.



Nothing long-lived exists anywhere in this chain. The Kubernetes token is short-lived and automatically rotated; the cloud credentials it yields are temporary. Compare this to Chapter 21's dynamic secrets — same principle, applied to cloud API access instead of database access, and it is the direct descendant of Chapter 19's OAuth federation applied to machine identity rather than human identity.



22.6 Secrets, correctly, in this environment



Chapter 21 established that Kubernetes Secret objects are base64, not encrypted — a point worth restating here because it is so routinely assumed otherwise. Three real fixes, in order of how much they change:



    

  • Encryption at rest for etcd — a cluster-level setting so the API server encrypts Secret data before writing it to etcd. Necessary, and it does not stop anyone with API access to read the Secret from doing so.
    • 

  • External secrets operators — the cluster holds only a reference; the actual value lives in a proper secrets manager or KMS (Ch. 21) and is synced or fetched at runtime.
    • 

  • No secret in Kubernetes at all — workload identity (above) obtains a credential directly from the cloud provider, so there is nothing sitting in etcd to protect in the first place. The strongest option, where it applies.
    •

Knowledge check


  

    
A NetworkPolicy allows ingress to a pod from the gateway only. What is the pod's egress posture?

    

      
      
      
      
    

    
NetworkPolicy is additive per direction. Selecting a pod with only an Ingress rule does not touch its egress at all — that remains fully open. This is the single most common Kubernetes network policy mistake, and it is silent: nothing errors, the policy simply does less than assumed.

  


  

    
Why does workload identity for cloud APIs eliminate the need for a long-lived static credential?

    

      
      
      
      
    

    
The chain is federation, not trust-by-origin: the cloud provider independently verifies the token's signature against Kubernetes' own published keys before issuing anything, and what it issues is temporary. Nothing long-lived exists anywhere in the path — the same shape as OIDC in Chapter 19, applied to machine rather than human identity.

  


  

    
A Kubernetes Secret holds a database password. What does base64 encoding actually provide?

    

      
      
      
      
    

    
Base64 exists so arbitrary binary data fits in a YAML/JSON field, not for confidentiality. Real protection requires etcd encryption at rest as a baseline, and ideally an external secrets manager or workload identity so the credential never sits in etcd as a Secret at all.

  


  

    
In a service mesh, how does a workload obtain its mTLS certificate?

    

      
      
      
      
    

    
The certificate's identity is derived from something Kubernetes already knows and can attest to — the service account — rather than from a domain name proven via ACME. This is why mesh certificates encode a namespace and service account rather than a hostname, and why they can safely rotate every few hours with zero manual involvement.

  





22.8 Carry forward


    

  • Ingress certificates and mesh workload certificates are two separate lifecycles, with different identities, issuers and trust anchors.
    • 

  • cert-manager turns Chapter 10's ACME flow into a declarative, self-renewing Kubernetes resource.
    • 

  • NetworkPolicy is additive and direction-specific — check egress separately, and confirm your CNI actually enforces it.
    • 

  • Pod hardening is Chapter 20's Linux-layer controls, applied per container: capabilities, filesystem, privilege escalation.
    • 

  • Workload identity eliminates static cloud credentials by federating a short-lived cluster-issued token.
    • 

  • A Kubernetes Secret is not a secret. Encrypt etcd, or better, keep the value out of Kubernetes entirely.
