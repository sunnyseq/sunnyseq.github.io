Web application security

TLS delivers bytes intact from one endpoint to another. It has nothing to say about whether those bytes should have been sent, or what the receiving application does with them. Almost every breach you have read about happened above the transport layer, on a connection with a perfectly valid padlock.

18.1 One idea underneath most of it

Chapter 1 defined a trust boundary as any line across which data changes trust level. Nearly every vulnerability in this chapter is the same failure: attacker-controlled data crossing a boundary and being interpreted rather than treated as inert.

VulnerabilityData crosses into……and is interpreted as
SQL injectionThe databaseQuery structure
XSSThe browserMarkup and script
Command injectionA shellCommands
Path traversalThe filesystemA path
SSRFYour networkA destination to fetch
DeserialisationThe runtimeObjects, sometimes code
Template injectionA template engineTemplate syntax

The fix has the same shape every time: separate data from structure at the interface, so no amount of hostile content can change the structure. Parameterised queries do this for SQL. Contextual escaping does it for HTML. execve with an argument array does it for shells. Sanitising, blocklisting and escaping-by-hand are all attempts to solve it inside the data, and all of them have a bypass.

Why filtering fails

A blocklist enumerates badness, and the attacker only needs one thing you did not think of. Encoding tricks, Unicode normalisation, double encoding, nested payloads that reassemble after your filter strips the inner one — the search space belongs to the attacker. Parameterisation is different in kind: the query structure is fixed before any user data is bound, so there is no parsing step for the data to influence. Prefer mechanisms that make the attack impossible over mechanisms that try to recognise it.

18.2 Cross-site scripting

XSS is script running in your origin, which means it inherits everything the origin can do: read the DOM, read non-HttpOnly cookies, make authenticated requests, and rewrite the page. Three variants:

  • Reflected — the payload is in the request and echoed into the response. Needs a crafted link.
  • Stored — the payload is persisted and served to everyone. The dangerous one.
  • DOM-based — no server involvement; client-side JavaScript writes untrusted data into a dangerous sink like innerHTML, document.write or eval.

Escaping is context-dependent, and this is where hand-rolled defences fail. The same string needs different treatment in HTML text, an attribute, a URL, inside a <script> block, or in CSS. Use a template engine that escapes automatically and knows the context; treat any manual escape as a smell.

18.4 CSRF, and what SameSite changed

The browser attaches your cookies to any request to a site, regardless of which page triggered it. So a form on evil.com posting to bank.example/transfer arrives fully authenticated. The application cannot tell it apart from a legitimate submission, because in every respect that matters it is one.

SameSite=Lax became the browser default around 2020 and removed most of this class: cookies are not sent on cross-site POSTs. It is a default, not a guarantee — older clients, deliberate SameSite=None for legitimate cross-site flows, and GET-based state changes all remain exposed. So keep a token defence for anything that changes state:

  • Synchroniser token — a random per-session value in the form, checked server-side. Still the standard.
  • Double-submit cookie — the same value in a cookie and a header; the attacker can cause the cookie to be sent but cannot read it to set the header. Weaker if subdomains are compromised.
  • Origin / Sec-Fetch-Site checks — modern browsers send these and they cannot be forged by page content.
Never use GET for state changes

A GET that changes state is reachable from an <img> tag, a link, a prefetch, or a corporate proxy warming its cache. SameSite=Lax deliberately still sends cookies on top-level GET navigations, so it does not protect these. This is also why 0-RTT early data (Ch. 13) is safe for GET and unsafe for anything else — the same idempotency requirement, arriving from a different direction.

18.5 SSRF

Your application fetches a URL the user supplied — a webhook, an image import, a PDF renderer. The request originates from inside your network, so it reaches things the user never could. In cloud environments the classic target is the instance metadata service at 169.254.169.254, which hands out credentials to anything that asks.

This was the 2019 Capital One breach: an SSRF in a WAF let an attacker reach metadata, retrieve IAM role credentials, and read over a hundred million records from S3.

Defences, in order of effectiveness:

  • Allowlist destinations where the use case permits. The only robust answer.
  • Egress network policy — the fetching workload should not be able to reach internal ranges or the metadata endpoint at all. This is a Chapter 22 control and it does not depend on getting the code right.
  • IMDSv2 — requires a PUT to obtain a token and rejects requests with a forwarded header, which defeats naive SSRF. Enforce it; v1 remains available otherwise.
  • Careful URL handling — and be aware that blocklisting IPs is fragile: DNS rebinding, redirects, IPv6 forms, decimal and octal encodings, and 0.0.0.0 all bypass naive checks.

18.7 Lab

Shell · audit a site's headers and cookies
# Every security-relevant response header, in one shot
curl -sSI https://example.com | grep -iE \
  'strict-transport|content-security|x-frame|x-content-type|referrer-policy|permissions-policy|set-cookie|cross-origin'

# Cookie flags \u2014 look for Secure, HttpOnly and SameSite on EVERY cookie
curl -sSI https://example.com | grep -i '^set-cookie' | while read -r c; do
  echo "$c"
  for f in Secure HttpOnly SameSite; do
    echo "$c" | grep -qi "$f" && echo "   \u2713 $f" || echo "   \u2717 $f MISSING"
  done
done

# Is HSTS strong enough to be preloaded?
curl -sSI https://example.com | grep -i strict-transport
#   Needs: max-age >= 31536000; includeSubDomains; preload
#   Check status: https://hstspreload.org/?domain=example.com

# Does the site redirect HTTP to HTTPS, and does HSTS then take over?
curl -sSI http://example.com | head -5

# CSP, readably
curl -sSI https://example.com | grep -i content-security-policy \
  | tr ';' '\n' | sed 's/^ */  /'
#   Look for 'unsafe-inline' and 'unsafe-eval' \u2014 both largely defeat the point.

# CORS: is the origin reflected? A reflecting server with credentials is a serious bug.
curl -sSI -H "Origin: https://evil.example" https://example.com/api/ \
  | grep -i 'access-control-allow'
#   Access-Control-Allow-Origin: https://evil.example  +  Allow-Credentials: true
#   = any site can read authenticated responses. Never reflect arbitrary origins.

# Subresource Integrity on third-party scripts
curl -sS https://example.com | grep -oE ']*src="https://[^"]*"[^>]*>' \
  | grep -v integrity= | head
#   Any external script without an integrity attribute is a CDN compromise away
#   from executing arbitrary code in your origin.

# Server-side: nginx headers worth setting
cat <<'NGINX'
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
add_header Content-Security-Policy   "default-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'" always;
add_header X-Content-Type-Options    "nosniff" always;
add_header Referrer-Policy           "strict-origin-when-cross-origin" always;
add_header Permissions-Policy        "geolocation=(), camera=(), microphone=()" always;
NGINX

Knowledge check

Why are parameterised queries a stronger defence against SQL injection than escaping input?

Escaping tries to neutralise dangerous characters inside the data, and the attacker gets unlimited attempts at encodings you did not anticipate. Parameterisation removes the parsing step entirely — the database receives a fixed structure plus values, and no value can alter the structure. Same principle as contextual auto-escaping for HTML and argument arrays for shells.

What does HttpOnly on a session cookie prevent?

It blocks document.cookie access. Note what it does not do: injected script can still make authenticated requests from within the page, because the browser attaches the cookie automatically. HttpOnly limits exfiltration, not abuse. The other three options describe Secure and SameSite.

An application fetches user-supplied URLs to generate link previews. What is the highest-value defence?

String blocklists are bypassed by DNS rebinding, redirects, IPv6 forms and decimal or octal encodings — the attacker controls the search space. A network control does not depend on parsing the URL correctly and holds even when the code is wrong. Combine with an allowlist and IMDSv2 where possible.

Which vulnerability category is consistently the most common in the OWASP Top 10?

It is rarely exotic — usually an endpoint that verifies you are authenticated but not that the record you asked for is yours. No cryptography involved, no clever payload, just a missing check. Authorisation must be enforced server-side, on every request, against the specific object being accessed.

18.8 Carry forward

  • Most web vulnerabilities are attacker data crossing a boundary and being interpreted as structure.
  • Separate data from structure at the interface. Filtering is a losing game.
  • Escaping is context-dependent; use an auto-escaping template engine.
  • Headers and cookie flags are cheap layers that fail independently of your code.
  • SameSite removed most CSRF but is not a substitute for tokens on state-changing routes.
  • SSRF is best solved at the network, not in the URL parser.
  • Broken access control is the biggest category, and it is usually a missing check.
