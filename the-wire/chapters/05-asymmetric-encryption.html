Asymmetric encryption

Two keys, mathematically bound, computationally impossible to derive one from the other. This is what lets two machines that have never met establish trust — and it is thousands of times slower than symmetric crypto, which is why it is used sparingly and never for bulk data.

5.1 The trapdoor idea

All public-key cryptography rests on a trapdoor one-way function: easy to compute forwards, infeasible to invert — unless you hold a secret that makes inversion easy.

RSAMultiply two large primesFactor the productKnowing p and q

Note the word "infeasible", not "impossible". Every one of these is breakable given enough computation. Security is an economic claim about time and energy, and Chapter 23 covers what happens when a quantum computer changes the economics of the middle two rows.

5.2 RSA, worked end to end

RSA is worth doing by hand once, because the mechanism is genuinely simple and demystifies the whole field.

KEY GENERATION
  1. Pick two large random primes            p, q          (1024 bits each for RSA-2048)
  2. n = p · q                                             the modulus — public
  3. λ(n) = lcm(p−1, q−1)                                  Carmichael totient
  4. Choose e coprime to λ(n)                e = 65537     public exponent
  5. d = e⁻¹ mod λ(n)                                      private exponent

  Public key  = (n, e)          Private key = (n, d)   [plus p, q for CRT speedup]

ENCRYPT / DECRYPT
  c = mᵉ mod n                  m = c^d mod n

WHY IT WORKS
  (mᵉ)^d = m^(ed) = m^(1 + kλ(n)) ≡ m  (mod n)     by Euler / Carmichael

WHY IT IS HARD
  Recovering d from (n, e) requires λ(n), which requires p and q,
  which requires factoring n.  For n of 2048 bits, nobody can.

Try to factor n by eye — with p and q this small it takes seconds, which is exactly why real keys use 1024-bit primes. Try m larger than n and watch it break: RSA can only encrypt values smaller than the modulus, which is one reason it is never used on bulk data.
Textbook RSA is broken

The scheme above, applied directly, is unusable. It is deterministic, so an attacker can encrypt candidate plaintexts and compare — devastating for a small message space like a PIN or a yes/no. It is also multiplicatively malleable: c₁·c₂ mod n decrypts to m₁·m₂, letting an attacker transform a ciphertext meaningfully. Real RSA always uses randomised padding: OAEP for encryption, PSS for signatures. The older PKCS#1 v1.5 padding is what Bleichenbacher's 1998 adaptive chosen-ciphertext attack broke, and variants of that attack — ROBOT in 2017 — were still finding vulnerable major sites nineteen years later.

5.3 Elliptic curves

ECC gets equivalent security from dramatically smaller keys, which matters because every byte of a handshake costs a round trip's worth of latency at scale.

The setting is the curve y² = x³ + ax + b over a finite field. Points on the curve form a group under a geometric addition rule: to add P and Q, draw the line through them, find the third intersection, and reflect it over the x-axis. Scalar multiplication kG means adding G to itself k times, done efficiently by double-and-add. The private key is the scalar k; the public key is the point kG. Recovering k from kG is the elliptic curve discrete logarithm problem, and the best known attacks are generic square-root methods costing about 2n/2.

Security levelRSA modulusECC keySymmetric equivalent
112-bit2048 bits224 bits3DES
128-bit3072 bits256 bitsAES-128
192-bit7680 bits384 bitsAES-192
256-bit15360 bits512 bitsAES-256

RSA scales terribly because index-calculus factoring methods are sub-exponential; ECC scales linearly because no such shortcut is known. A 256-bit ECC key matches a 3072-bit RSA key, and this gap only widens.

Which curves

  • P-256 / secp256r1 — NIST, ubiquitous, mandatory-to-implement in TLS. Its unexplained seed constants attract suspicion, though no break is known.
  • X25519 — Bernstein's Curve25519 for key exchange. Rigid parameters with a documented derivation, no invalid-curve pitfalls, fast constant-time implementations, and every byte string is a valid key. The default in TLS 1.3 and in SSH.
  • Ed25519 — the same curve for signatures (Ch. 7).
  • secp256k1 — Bitcoin's curve. Fine, but not used in TLS.
A caution about invalid curves

If an implementation does not verify that a received point actually lies on the expected curve, an attacker can send a point on a weaker related curve and recover the private key from a handful of exchanges. This is a real, repeatedly exploited bug class in Weierstrass-form curves such as P-256. X25519's design sidesteps it — every 32-byte string is a legitimate input — which is one of the strongest practical arguments for preferring it.

5.4 What asymmetric crypto is actually used for

Not bulk data. RSA-2048 encrypts at roughly a hundred kilobytes per second; AES-GCM with hardware support runs at gigabytes per second — a difference of four to five orders of magnitude. So the universal pattern is hybrid encryption: use asymmetric cryptography once to establish or transport a symmetric key, then do all the real work symmetrically.

1. Establish a shared symmetric key       ← asymmetric, once per session
2. Encrypt everything with AEAD           ← symmetric, for the rest of time

Step 1 has two possible shapes, and the difference between them is the most important operational distinction in TLS:

Key transport (RSA)Key agreement (ECDHE)
MechanismClient picks the secret, encrypts it to the server's public keyBoth sides contribute; neither transmits the secret
Forward secrecyNo. Recorded traffic is decryptable if the server's key later leaks.Yes. Ephemeral keys are discarded after the handshake.
Status in TLSRemoved entirely in TLS 1.3The only option in TLS 1.3

That single row — forward secrecy — is why key transport was deleted from the protocol, and it is the subject of Chapter 6.

5.5 Lab

Shell · generate, inspect, measure
# Generate an RSA key and look inside it
openssl genrsa -out rsa.pem 2048
openssl rsa -in rsa.pem -noout -text | head -8
#   modulus (n), publicExponent (e = 65537), privateExponent (d),
#   prime1 (p), prime2 (q), and the CRT coefficients used for fast decryption

# The public half is tiny by comparison
openssl rsa -in rsa.pem -pubout -out rsa.pub.pem && cat rsa.pub.pem

# An EC key at comparable-or-better strength — note the size difference
openssl ecparam -name prime256v1 -genkey -noout -out ec.pem
openssl ec -in ec.pem -noout -text | head -6
ls -l rsa.pem ec.pem

# Measure the gap that forces hybrid encryption
openssl speed rsa2048 ecdsap256 2>/dev/null | tail -6
openssl speed -evp aes-256-gcm 2>/dev/null | tail -2

# Encrypt a small file with RSA-OAEP (note the size limit!)
echo "a 32-byte session key would go here" > small.txt
openssl pkeyutl -encrypt -inkey rsa.pem -pubin -in small.txt -out small.enc \
  -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 2>/dev/null \
  || openssl pkeyutl -encrypt -inkey rsa.pub.pem -pubin -in small.txt -out small.enc \
       -pkeyopt rsa_padding_mode:oaep
openssl pkeyutl -decrypt -inkey rsa.pem -in small.enc -pkeyopt rsa_padding_mode:oaep

# Now try a file larger than the modulus and read the error carefully
head -c 500 /dev/urandom > big.bin
openssl pkeyutl -encrypt -inkey rsa.pub.pem -pubin -in big.bin -out big.enc \
  -pkeyopt rsa_padding_mode:oaep   # fails: data too large for key size

Knowledge check

Why is textbook RSA — no padding — unusable in practice?

Determinism means an attacker can encrypt guesses and match against a captured ciphertext — fatal when the plaintext space is small. Malleability means multiplying two ciphertexts multiplies the plaintexts, which is a real attack primitive. OAEP fixes both by injecting randomness and structure.

A 256-bit ECC key is roughly equivalent in strength to an RSA key of what size?

Factoring has sub-exponential algorithms, so RSA key sizes must grow steeply for each additional security bit. Elliptic curve discrete log has only generic square-root attacks, so ECC key size grows linearly — hence 256 bits of ECC ≈ 3072 bits of RSA ≈ AES-128.

Why is asymmetric cryptography almost never used to encrypt bulk data?

Both constraints bite. RSA-2048 handles at most 245 bytes per operation with OAEP, and runs four to five orders of magnitude slower than hardware AES. Hence the hybrid pattern: asymmetric once to agree a key, symmetric for everything after.

Why does TLS 1.3 remove RSA key transport entirely?

With key transport the client encrypts the session secret to the server's long-term key, so that key can unlock any recorded session forever. Ephemeral key agreement destroys the exchange keys after the handshake, so a later compromise of the certificate key recovers nothing. That is Chapter 6.

5.6 Carry forward

  • Public-key crypto rests on trapdoor functions; "hard" is an economic claim, not an absolute one.
  • Never use raw RSA. OAEP for encryption, PSS for signatures, always.
  • ECC gives the same strength in a fraction of the bytes, and the gap widens with every security level.
  • Asymmetric crypto establishes keys; symmetric crypto carries data. Always hybrid.
  • Key transport and key agreement look similar and differ in exactly one crucial way.
