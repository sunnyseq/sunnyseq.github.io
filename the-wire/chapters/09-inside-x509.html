Inside an X.509 certificate

Chapter 8 treated certificates as opaque signed assertions. Open one and it is a rigid, decades-old data structure with genuinely strange corners — a 1988 telecoms standard that the entire web now depends on, complete with fields nobody uses and one famous bug that came from a field everyone ignored.

9.1 The shape of the thing

An X.509 certificate has exactly three top-level parts. Understanding this split explains most of what follows.

Certificate ::= SEQUENCE {
    tbsCertificate       TBSCertificate,      -- "to be signed": everything that matters
    signatureAlgorithm   AlgorithmIdentifier, -- how it was signed
    signatureValue       BIT STRING           -- the signature itself
}

The signature covers the DER encoding of tbsCertificate and nothing else. That is why altering any field invalidates the certificate, and also why signatureAlgorithm appears twice — once inside the signed portion and once outside. A verifier must check the two match. Trusting the outer, unsigned copy is an algorithm-substitution attack: an attacker downgrades the stated algorithm to something they can forge.

9.3 SAN versus CN, and why CN is dead

The original design put the hostname in the Subject's Common Name — a field intended for a person's name in an X.500 directory. It was pressed into service for hostnames, and it was a poor fit: no structure, no way to express multiple names, no way to distinguish a DNS name from an IP address or an email address.

Subject Alternative Name replaced it, and is now the only field that counts. Since 2017 Chrome and then every other major browser ignore CN entirely — a certificate with the hostname only in CN fails, no matter how correct everything else is. SAN carries typed entries:

X509v3 Subject Alternative Name:
    DNS:bank.example, DNS:www.bank.example, DNS:*.api.bank.example,
    IP Address:203.0.113.10, otherName:1.3.6.1.4.1.311.20.2.3;UTF8:svc@cluster.local
Wildcard rules are narrower than people expect

*.example.com matches a.example.com but not example.com itself, and not a.b.example.com. The wildcard covers exactly one label, and only the leftmost one. *.*.example.com and a*.example.com are not valid. If you need the apex and the subdomains, both must appear in SAN — which is why real certificates routinely list example.com and *.example.com together.

9.5 ASN.1, DER and PEM

Three layers people conflate constantly:

  • ASN.1 is the abstract schema language — it defines that a certificate is a SEQUENCE containing an INTEGER serial, a Name, and so on. It says nothing about bytes.
  • DER (Distinguished Encoding Rules) is the concrete byte encoding, and crucially it is canonical: there is exactly one valid DER encoding of any given structure. That matters enormously, because signatures are computed over bytes. If two encodings of the same certificate were possible, signature verification would be ambiguous.
  • PEM is DER, base64-encoded, wrapped in -----BEGIN CERTIFICATE----- markers, so it survives being pasted into config files and emails.

Every DER element is a triple: tag, length, value. Switch the inspector above to the byte view to see it. Tag 0x30 is SEQUENCE, 0x02 is INTEGER, 0x06 is OBJECT IDENTIFIER, 0x03 is BIT STRING. Lengths under 128 are a single byte; longer ones set the high bit of the first byte to say how many length bytes follow.

The null-byte attack, and why canonical parsing matters

In 2009 Moxie Marlinspike demonstrated certificates with a CN of bank.example\0evil.com. Some CAs validated ownership of evil.com — reading to the end — while C-based clients compared with string functions that stopped at the null byte and saw bank.example. A legitimately issued certificate, accepted for a domain the holder did not own. ASN.1 strings are length-prefixed and can legally contain nulls; C strings cannot. The lesson generalises far beyond X.509: wherever a validator and a consumer parse the same bytes differently, that difference is the vulnerability.

9.6 Fields that are not what they look like

  • Serial number is not a counter. The CA/Browser Forum requires at least 64 bits of entropy in it, because that randomness is a defence against chosen-prefix collision attacks on the signature hash — an attacker who cannot predict the serial cannot construct a colliding certificate. The 2008 rogue-CA MD5 attack depended on sequential serials.
  • notBefore / notAfter use UTCTime for years before 2050 (two-digit years, genuinely) and GeneralizedTime afterwards. Public TLS certificates are now capped at 398 days, moving to 47 days by 2029.
  • Issuer and Subject are X.500 Distinguished Names — an ordered sequence of attribute sets, not a string. The CN=x, O=y, C=z rendering is a display convention. Path building matches these as structures, and byte-level comparison of the rendered string is a bug.
  • Version is zero-indexed: v3 encodes as the integer 2. Extensions only exist in v3, so effectively every certificate you will meet is v3.

9.7 Lab

Shell · take a certificate apart
# Grab a real certificate to work with
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -out cert.pem

# Full human-readable dump
openssl x509 -in cert.pem -noout -text

# The fields individually
openssl x509 -in cert.pem -noout -subject -issuer -serial -dates -fingerprint -sha256
openssl x509 -in cert.pem -noout -ext subjectAltName
openssl x509 -in cert.pem -noout -ext basicConstraints,keyUsage,extendedKeyUsage
openssl x509 -in cert.pem -noout -pubkey

# PEM is just base64-wrapped DER. Prove it.
openssl x509 -in cert.pem -outform DER -out cert.der
ls -l cert.pem cert.der
base64 -w0 cert.der | head -c 64; echo
grep -v -- ----- cert.pem | tr -d '\n' | head -c 64; echo   # identical

# Walk the raw ASN.1 structure, tag by tag
openssl asn1parse -in cert.pem -i | head -40
#   Read the indentation as nesting. Find the two AlgorithmIdentifiers and
#   confirm they match — a verifier that skips this check is exploitable.

# Look at the first bytes by hand
xxd -l 48 cert.der
#   30 82 xx xx  -> SEQUENCE, length in the next 2 bytes (high bit set = long form)
#   a0 03 02 01 02 -> [0] EXPLICIT, INTEGER 2  -> version v3

# Verify the signature yourself, without trusting any library's chain logic
openssl x509 -in cert.pem -noout -text | grep -A1 'Signature Algorithm' | head -2

# Test wildcard matching rules for real
openssl x509 -in cert.pem -noout -checkhost example.com
openssl x509 -in cert.pem -noout -checkhost sub.example.com
openssl x509 -in cert.pem -noout -checkhost evil.com

Knowledge check

Why does signatureAlgorithm appear both inside tbsCertificate and outside it?

The outer copy sits outside the signed region, so an attacker can change it freely. If a verifier believes it, they can be steered toward a weaker algorithm the attacker can forge. The inner copy is covered by the signature; the check is that they agree.

A certificate has SAN DNS:*.example.com. Which hostname does it validate for?

A wildcard covers exactly one label, and only the leftmost. The apex needs its own SAN entry, and deeper subdomains need their own wildcard. This is why real certificates commonly list both example.com and *.example.com.

Why does the CA/Browser Forum require at least 64 bits of entropy in the serial number?

To forge a certificate via a hash collision, an attacker must predict the exact bytes the CA will sign. A random serial makes that impossible even if the hash function weakens. The 2008 rogue-CA attack against MD5 worked partly because the target CA used sequential serials.

What does marking an extension critical mean?

Everything in tbsCertificate is signed, critical or not. The critical flag is a forward-compatibility mechanism: it lets a new, security-relevant constraint be added to a format from 1988 without old clients silently ignoring it and accepting something they should not.

9.8 Carry forward

  • The signature covers tbsCertificate only. Both copies of the algorithm identifier must be compared.
  • SAN is the identity. CN is dead and has been ignored by browsers since 2017.
  • Wildcards cover exactly one leftmost label — never the apex, never two levels.
  • DER is canonical because signatures are over bytes. PEM is just base64 DER.
  • Critical extensions are how a 1988 format safely gained new mandatory checks.
  • Where a validator and a consumer parse the same bytes differently, that gap is the vulnerability.
