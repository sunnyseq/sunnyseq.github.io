Secrets and key management

Every chapter in this course has eventually arrived at a key that needs protecting — a certificate's private key, a symmetric session key, a signing key, an HMAC secret. This chapter is about the layer beneath all of them: where keys physically live, how one key protects a million others, and why "just put it in an environment variable" is the default that keeps causing breaches.

21.1 The hierarchy of custody

Where the key livesExtraction costTypical use
Source code, config file, env varTrivial — grep, a leaked log, a compromised hostWhere most secrets actually live, unfortunately
Secrets manager (Vault, cloud KMS/Secrets Manager)Requires compromising the manager or a legitimate caller's credentialsApplication secrets, database credentials, API keys
Software KMS with envelope encryptionRequires compromising the KMS's own key custodyData-at-rest encryption at scale
HSM — hardware security modulePhysically hard; the key never leaves the device in plaintextCA roots, code-signing keys, payment keys

The trend down that table is the same trend from Chapter 8's root CA custody and Chapter 16's mesh certificates: the highest-value keys should never be directly usable by software at all, only invokable through an interface that performs an operation and returns a result, never the key itself.

21.2 What an HSM actually buys you

A hardware security module is a tamper-resistant device that generates and holds keys, and performs cryptographic operations without ever exposing the key material outside its boundary. The operative word is boundary: you send it a message to sign, and it sends back a signature. You cannot ask it for the key.

  • Tamper resistance and evidence. Physical intrusion attempts trigger key zeroisation. Certified devices are rated against defined physical attack levels (FIPS 140-3, Common Criteria).
  • Non-extractability. Even an attacker with root on the host cannot read the key, because it was never in host memory to begin with.
  • Audit. Every operation is logged by the device itself, independent of the (possibly compromised) application asking for it.

The trade-offs are real: cost, latency per operation, and a single choke point for availability. This is exactly why root CA keys live in an HSM brought out for a witnessed ceremony (Ch. 8) while leaf certificates are issued by software thousands of times a second — the cost is worth paying once, at the top of the hierarchy, and not at every leaf.

Cloud HSM, without owning hardware

AWS CloudHSM, Azure Managed HSM, and Google Cloud HSM offer FIPS 140-3 validated hardware as a service. You still hold ultimate custody — the cloud provider cannot extract your keys either — and you avoid needing your own datacentre and ceremony process. For most organisations this is the right trade, reserving physically-owned HSMs for the handful of cases with regulatory or sovereignty requirements that demand it.

21.3 Envelope encryption

You cannot practically run every encryption operation through an HSM or a KMS — the latency and cost don't scale to encrypting millions of objects. Envelope encryption solves this with the same asymmetric-then-symmetric hybrid pattern from Chapter 5, one level up.

Interactive · envelope encryption—
The KMS is called once, briefly, to wrap or unwrap a tiny key. It never sees the object being encrypted, and the object's DEK never touches disk in plaintext.
encrypt(object):
  DEK = random 256-bit key                     # generated locally, once per object
  ciphertext = AES-GCM(DEK, object)             # Chapter 4, entirely local, fast
  wrapped_DEK = KMS.Encrypt(KEK, DEK)           # ONE small call to the KMS/HSM
  store(ciphertext, wrapped_DEK)                # the KEK never leaves the KMS

decrypt(ciphertext, wrapped_DEK):
  DEK = KMS.Decrypt(KEK, wrapped_DEK)           # KMS unwraps, returns the DEK
  object = AES-GCM-decrypt(DEK, ciphertext)     # local, fast

The KEK (key encryption key) never leaves the KMS or HSM in plaintext, ever. The DEK (data encryption key) exists in plaintext only briefly, in memory, at the moment of use. This bounds a KMS compromise to "an attacker can ask it to unwrap keys" rather than "an attacker now holds the master key" — and it bounds a memory disclosure to whatever DEKs happened to be in use at that instant, not your entire estate. Compare this directly to session tickets in Chapter 15: same asymmetry between a long-term wrapping key and short-lived working keys, same reasoning.

21.4 Rotation

A key that is never rotated is a growing liability: more time to be stolen unnoticed, more data protected by a single point of failure, and — for signing keys — a larger corpus for cryptanalysis. Rotation policy differs by key class:

KeyTypical lifetimeWhy
TLS certificate47–398 days, shrinking (Ch. 10)Bounds a compromise; substitutes for revocation
Session ticket keyHoursPreserves forward secrecy (Ch. 6, 15)
Mesh workload certificateHoursMakes revocation irrelevant (Ch. 16)
KEK / master keyAnnually, or on suspected compromiseRe-wrap DEKs; old KEK versions kept for decrypting old data
Database credentialMinutes to hours — dynamic secretsA leaked credential expires before it is useful
Root CA key10–25 yearsOffline, ceremony-issued; rotation is a major event

Rotating a KEK does not mean re-encrypting every object — it means wrapping future DEKs under the new KEK while keeping the old KEK available to unwrap existing ones, versioned. This is the same "keep the previous key briefly" pattern as session ticket rotation in Chapter 15, at a different point in the hierarchy.

Dynamic secrets

The most effective rotation is automatic and short-lived by construction. Rather than a static database password living in a config file for months, a secrets manager issues a unique credential per application instance, valid for an hour, and revokes it automatically. A leaked credential in a log file is worthless by the time anyone finds it. This is the database analogue of Chapter 16's mesh certificates — the same insight, applied to a different credential type.

21.5 Where secrets actually leak

The recurring failure modes
  • Committed to version control. Once pushed, a secret is compromised even if the commit is later removed — git history, forks, and CI caches all retain it. Treat any committed secret as burned and rotate it; do not merely delete the line.
  • Baked into container images. A secret set via ARG or an early ENV persists in an intermediate layer even if a later layer removes it. Anyone who can pull the image can extract it.
  • Logged. Debug logging that dumps request objects, headers, or environment variables routinely captures secrets verbatim into log aggregation systems with much wider read access than the secret's owner intended.
  • Passed as CLI arguments. Process arguments are visible to every other user on the host via ps. Use stdin, a file with restricted permissions, or an environment variable read once at startup instead.
  • Left in CI/CD variables with no scoping. A secret available to every pipeline is available to every contributor who can trigger one, and to any dependency that pipeline pulls in — which is exactly the supply-chain concern this course flagged but did not expand on.

21.6 Secret scanning

Detection is a necessary backstop for the failure modes above, not a substitute for preventing them. Tools like gitleaks, TruffleHog, and GitHub's native secret scanning work by pattern-matching known credential formats (AWS keys, database connection strings, JWTs) plus entropy analysis for anything that looks like random key material.

# A minimal pre-commit hook using gitleaks
gitleaks detect --source . --verbose --redact

# What it looks for, roughly:
#  - high-Shannon-entropy strings in likely secret contexts (assignments, env files)
#  - known prefixes: AKIA (AWS), ghp_ (GitHub), sk_live_ (Stripe), xox[bp]- (Slack)
#  - private key PEM headers appearing anywhere in a diff

Run scanning at commit time, not only in CI — catching a secret before it is pushed is strictly better than catching it after, because the git history problem above only exists once something has actually been pushed.

21.7 Lab

Shell · envelope encryption and scanning, for real
# Simulate envelope encryption with local OpenSSL standing in for a KMS
# 1. Generate a "KEK" \u2014 imagine this never leaves an HSM
openssl rand 32 > kek.bin

# 2. Generate a DEK locally, per object
openssl rand 32 > dek.bin

# 3. Encrypt the actual data with the DEK \u2014 fast, local, no KMS call
openssl enc -aes-256-gcm -K $(xxd -p -c 64 dek.bin) -iv $(openssl rand -hex 12) \
  -in largefile.dat -out largefile.enc 2>/dev/null || echo "(demo: assume largefile.dat exists)"

# 4. "Wrap" the DEK under the KEK \u2014 this is the only thing that touches the KMS
openssl enc -aes-256-gcm -K $(xxd -p -c 64 kek.bin) -iv $(openssl rand -hex 12) \
  -in dek.bin -out dek.wrapped

# Notice: kek.bin is used ONCE, briefly, to wrap a 32-byte key.
# It is never used on the actual object, and in a real KMS it never
# leaves the device at all \u2014 you would call an API, not touch a file.
ls -la kek.bin dek.bin dek.wrapped largefile.enc 2>/dev/null

# Real cloud KMS envelope encryption (AWS example, needs credentials)
aws kms generate-data-key --key-id alias/my-kek --key-spec AES_256 2>/dev/null \
  | python3 -m json.tool
#   Returns both a plaintext DEK (use immediately, then discard) and a
#   CiphertextBlob (the wrapped DEK, safe to store alongside your data).

# Scan a repo for secrets before they ever reach a remote
pip install --user detect-secrets 2>/dev/null
gitleaks detect --source . -v 2>/dev/null || echo "install gitleaks to run this"

# Prove CLI arguments are visible to other users
sleep 60 --dummy-secret=hunter2 &

kill %1

# Check what actually ended up in a container image layer
docker history --no-trunc your-image:latest 2>/dev/null | grep -i -E 'ENV|ARG' | head
#   A secret set via ARG/ENV and later "removed" is often still sitting

Knowledge check

In envelope encryption, what does the KMS actually see and touch?

The KMS's role is narrow by design: wrap or unwrap a 256-bit key. The actual object is encrypted locally with that key, fast and without a network round trip per object. This is what lets envelope encryption scale to millions of objects against a KMS that could never handle that call volume directly.

Why does an HSM protect a key even against an attacker with root access to the host?

Root on the host lets an attacker read anything the host holds — but the key was never handed to the host. The application sends data to sign or decrypt and receives a result; the key itself never crosses the boundary. This is precisely why root CA keys live this way (Ch. 8) rather than as a file an operator could read.

A secret was committed to a private repository and removed in the next commit. What is the correct response?

Git history, CI caches, forks, and any clone made before the fix can retain the secret indefinitely. History rewriting helps hygiene going forward but cannot guarantee every copy is gone. The only response that actually closes the exposure is rotating the credential itself.

Why are dynamic, short-lived database credentials preferred over a long-lived shared password?

This mirrors session ticket rotation (Ch. 15) and mesh certificate lifetimes (Ch. 16): the same insight — bound the value of a leak by bounding the credential's lifetime — applied to database access. A static password sitting in a config file for months is a liability that grows every day it is not rotated.

21.8 Carry forward

  • The highest-value keys should be invokable, never extractable — an HSM boundary, not a file an operator can read.
  • Envelope encryption lets one protected key secure unlimited data, without every operation touching the KMS.
  • Rotation policy should match the key's blast radius: hours for working keys, years for roots, with old versions retained to decrypt existing data.
  • Dynamic, short-lived credentials bound the damage of a leak better than any amount of careful handling of a static one.
  • Secrets leak through commits, images, logs, process arguments, and unscoped CI variables — prevention and scanning both matter, and scanning is a backstop, not a plan.
