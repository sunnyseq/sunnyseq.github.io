Authentication and authorization

Two words that get used interchangeably and should never be. Authentication asks who are you; authorization asks what may you do. Systems that conflate them produce the largest vulnerability category in the OWASP list, and the confusion usually shows up as a check performed once at the door and never again.

19.1 The distinction, and why it keeps failing

AuthenticationAuthorization
QuestionWho is this?May they do this, to this object?
WhenOnce, at the startEvery single request
EvidencePassword, key, certificate, passkeyRoles, ownership, policy
Failure looks likeAccount takeoverReading someone else's data

The classic bug is an endpoint that verifies a valid session and then trusts an identifier from the request: GET /invoices/8842 returns invoice 8842 to anyone logged in. Authentication succeeded perfectly. Nobody asked whether this user owns that invoice. This is insecure direct object reference, and it is a one-line fix that is missing across an enormous amount of production code.

The rule worth internalising

Authorization is a property of the tuple (subject, action, object), evaluated server-side, on every request. Not of the route. Not of the UI. Hiding a button changes what a user sees, never what they can send. If the check lives anywhere other than immediately before the action, it is decorative.

19.2 Passwords, and doing them properly

Chapter 3 covered the storage side: Argon2id, memory-hard, deliberately slow. The surrounding practice matters as much:

  • Length over composition. NIST SP 800-63B dropped mandatory complexity rules and forced rotation, because both push users toward predictable patterns. Require a minimum length, allow long passphrases, allow paste, and support the full Unicode range.
  • Check against breach corpora. Blocking known-compromised passwords at signup stops credential stuffing at the source. Have I Been Pwned's range API lets you do this without sending the password — you send the first five hex characters of its SHA-1 and check locally against the returned suffixes. That is k-anonymity applied to a lookup.
  • Rehash on login when your work factor increases, since that is the only moment you hold the plaintext.
  • Constant-time comparison, and identical timing and messaging whether or not the account exists — otherwise login becomes a user enumeration oracle (Ch. 2).

19.3 The second factor, ranked honestly

FactorPhishing-resistant?Notes
SMS one-time codeNoSIM swap, SS7 interception, and trivially relayed. Better than nothing; do not call it strong.
TOTP appNoNo network dependency, but a phishing site simply asks for the code and relays it within its 30-second window.
Push approvalNoVulnerable to MFA fatigue — spam prompts until someone taps accept. Number matching helps.
WebAuthn / passkeysYesThe signature is bound to the origin. A phishing site gets nothing usable.
Client certificatesYesSame property (Ch. 16), worse ergonomics for consumers.

The dividing line is not strength but binding. Anything the user can read and retype can be relayed by a site pretending to be you. WebAuthn signs a challenge together with the origin the browser is actually on, and the browser will not sign for the wrong origin — so a credential harvested at bank-secure.example is worthless at bank.example. That is exactly the mechanism from Chapter 16, with usable enrolment and recovery bolted on.

The revocation row decides most cases. If a user changes their password or an admin disables an account, a session dies instantly and a JWT does not. The usual answer — short access tokens plus a refresh token — is really an admission that you need server state after all, since the refresh token has to be revocable. For a normal web application, boring server-side sessions are usually the right choice, and JWTs are frequently adopted for statelessness that the architecture does not actually require.

19.5 OAuth 2.0 and OpenID Connect

The distinction people get wrong: OAuth is a delegated authorization protocol, not an authentication protocol. It answers "may this application access that resource on the user's behalf?" OIDC is a thin layer on top that adds authentication properly, via an ID token with defined claims and validation rules. Using raw OAuth to log people in is a well-documented source of bugs.

PKCE was designed for mobile apps that cannot keep a client secret, and is now recommended for every client type including server-side web apps. It costs one hash and closes an entire attack class.

Flows you should not use

  • Implicit flow — returns the access token directly in the URL fragment, where it lands in browser history, referrer headers and logs. Deprecated; use authorization code with PKCE.
  • Resource owner password credentials — the application collects the user's password for the identity provider. Defeats the entire purpose of delegation, and is incompatible with MFA and passkeys.

19.6 Authorization models

  • RBAC — permissions attach to roles, users get roles. Simple, auditable, and it degrades into role explosion when rules depend on context.
  • ABAC — decisions are computed from attributes of subject, object, action and environment. Expressive, and harder to reason about or audit.
  • ReBAC — permission follows a relationship graph: you may edit this document because you own the folder that contains it. This is Google's Zanzibar model, and it fits the ownership-and-sharing shape most applications actually have.

Whichever you choose, two implementation rules matter more than the model. Deny by default — an unmatched request is refused, so a forgotten rule fails closed (Ch. 1). And decide centrally, enforce locally — a policy engine keeps rules consistent and reviewable, but the enforcement point must sit immediately before the action, never at the edge on the assumption that internal callers are trustworthy (Ch. 1's TB-2, Ch. 16).

# Decode a JWT without any library \u2014 note you need no key to READ it
T='eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0IiwiZXhwIjoxNzAwMDAwMDAwfQ.sig'

done
#   Signed, not encrypted. Never put secrets in a payload.

# Check a password against breach corpora WITHOUT sending it (k-anonymity)
P='correct horse battery staple'
H=$(printf '%s' "$P" | sha1sum | cut -d' ' -f1 | tr 'a-z' 'A-Z')
curl -s "https://api.pwnedpasswords.com/range/${H:0:5}" | grep -i "${H:5}" \
  && echo "BREACHED \u2014 reject at signup" || echo "not found in corpus"
#   Only the first 5 hex characters leave your machine.

# Password hashing with sane parameters, and how long one verify costs
time python3 -c "
import argon2
h = argon2.PasswordHasher(memory_cost=65536, time_cost=3, parallelism=4)
d = h.hash('correct horse battery staple')
print(d)
print('verify:', h.verify(d, 'correct horse battery staple'))"

# Generate a PKCE pair the way a client would
VERIFIER=$(openssl rand -base64 96 | tr -d '\n=+/' | cut -c1-64)
CHALLENGE=$(printf '%s' "$VERIFIER" | openssl dgst -sha256 -binary | base64 | tr '+/' '-_' | tr -d '=')
echo "code_verifier : $VERIFIER"
echo "code_challenge: $CHALLENGE"
#   The challenge goes in the authorization request; the verifier is only
#   revealed at the token exchange. An intercepted code is useless without it.

# An identity provider's OIDC configuration \u2014 every field it advertises
curl -s https://accounts.google.com/.well-known/openid-configuration | python3 -m json.tool | head -30

# The signing keys used to verify ID tokens
curl -s https://www.googleapis.com/oauth2/v3/certs | python3 -m json.tool | head -20

# Session cookie hygiene on your own app (Ch. 18)
curl -sSI https://your-app.example/login | grep -i set-cookie

# User enumeration: do wrong-password and wrong-username behave identically?
for u in realuser@example.com definitely-not-a-user@example.com; do
  printf '%-40s ' "$u"
  curl -s -o /dev/null -w '%{http_code}  %{time_total}s\n' \

done
#   Different status codes or noticeably different timings = an enumeration oracle.

Knowledge check

An endpoint checks that the request has a valid session, then returns the record whose ID is in the URL. What is wrong?

Insecure direct object reference, and consistently the largest OWASP category. Authorization is a property of (subject, action, object) and must be evaluated per request against the specific object. Making IDs unguessable is obfuscation, not a control.

Why is TOTP not phishing-resistant while WebAuthn is?

The property is binding, not strength. Anything a human can transcribe can be relayed within its validity window. WebAuthn includes the origin in the signed data and the browser enforces it, so a credential harvested on a lookalike domain is worthless on the real one — the same mechanism as mTLS in Chapter 16.

What does PKCE protect against?

The client commits to a secret verifier by sending its hash up front, then reveals the verifier only at the token exchange. A code stolen from a redirect — a malicious app registered for the same URI scheme, a logged URL, a referrer leak — cannot be redeemed. Originally for mobile clients; now recommended for all of them.

A team chose JWTs so their API could scale statelessly. Which problem should they plan for?

Password changes, account suspension and stolen tokens all need immediate effect, and a self-contained token gives none. Short expiry plus a revocable refresh token is the standard answer, and it reintroduces server state — which is worth noticing before choosing the architecture. JWTs are signed, not encrypted, so anyone holding one can read it.

19.8 Carry forward

  • Authentication happens once; authorization happens on every request, against the specific object.
  • Length beats complexity, and check passwords against breach corpora at signup.
  • Phishing resistance comes from origin binding, not from factor strength.
  • Sessions revoke instantly; JWTs do not. Choose on that, not on fashion.
  • OAuth authorizes; OIDC authenticates. Use authorization code with PKCE, always.
  • Deny by default, decide centrally, enforce locally.
